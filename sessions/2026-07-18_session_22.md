## What happened

### Rate limiting via the native Workers binding

Chose Cloudflare's **native Workers Rate Limiting binding** over the plan's
KV/Durable-Object sketch. It needs no namespace provisioned (the `namespace_id`
is an arbitrary account-local number) and no account step beyond `wrangler
deploy`, which removed the "needs your infra" blocker entirely.

- **Pure decision seam.** `src/lib/rate-limit.ts` exposes a `RateLimiter`
  interface (mirroring the binding's `limit({ key }) → { success }`) and
  `withinRateLimit(limiter, key)`. It **fails open**: unbound or throwing → the
  request is allowed. The limiter is a flood brake ahead of a human-gated PR
  queue, not the admission gate, so a limiter hiccup must never reject a
  legitimate proposal. Unit-tested (5 cases): unbound, allow, block, throw,
  key-passthrough.
- **Worker wiring.** The check sits in `handleProposal` right after identity
  resolution and before any GitHub work, keyed `proposal:<tokenId>`, so one
  leaked or runaway credential cannot open an unbounded burst of PRs. Over the
  limit returns `429` with a `Retry-After` header and a structured
  `{ code: "rate_limited", retryAfterSeconds }` body. Because it runs after auth,
  an unauthenticated caller still gets `401`.
- **Config.** `PROPOSAL_LIMITER` in `wrangler.jsonc`, `10 requests / 60s`. The
  code constant `RATE_LIMIT_PERIOD_S` mirrors the period for the `Retry-After`
  hint.

### Verified live

Deployed, then flooded the live endpoint with authenticated requests carrying an
**invalid body** — so each passes the rate-limit check but fails JSON parsing
before any PR is created (no side effects). Result: requests flipped to `429`
right at the threshold (it allowed 11 before blocking — the binding's documented
"permissive, eventually consistent" tolerance), the `429` carried
`retry-after: 60` and the structured body, and an unauthenticated request stayed
`401`.

## Decisions worth remembering

- **Native binding, not KV/DO.** For a *flood brake* the native binding is the
  right tool and needs nothing provisioned. Its bounds are honest and documented
  (`worker/README.md`): a per-minute burst cap, not a per-hour/day quota (period
  is 10 or 60s only), and per-Cloudflare-location + eventually consistent, so the
  cap is approximate. A longer-window quota would still need KV or a Durable
  Object.
- **Fail open, on purpose.** Defense-in-depth in front of a human gate should
  degrade to "allowed", never to "legitimate work rejected".
- **Test the write path with an invalid body.** Placing the limiter before the
  JSON parse means over-limit authenticated requests can be exercised live
  without opening a single PR.
