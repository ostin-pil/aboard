## What happened

### 1. S1, the unescaped `ld+json` embed

`ldJsonScript()` in `src/lib/jsonld.ts` stringifies and replaces every
`<` with its JSON unicode escape, used at both embed sites. Escaping that
one character is sufficient rather than merely convenient: a script
element's content is raw text, so the parser is not entity-decoding, and
every exit from the element (`</script`, and `<!--`, which opens a
comment state) begins with `<`.

Four tests in `jsonld.test.ts`, including a round-trip so the escape is
provably lossless. Removing the escape fails two of them, quoting the
injected `</script><img src=x onerror=...>`. A scan of the built `out/`
found 30 embedded blocks, all parsing, none carrying a raw `<`.

The API routes deliberately keep bare `JSON.stringify`: no HTML parser
sits in that path, so their bytes stay exactly what `v0.json` describes
and the schema needed no edit.

### 2. S2, a body cap that actually caps

`MAX_PROPOSAL_BYTES` checked only the declared `content-length`, which
the caller writes and a chunked request omits entirely, and
`readEnvelope()` then buffered the whole body regardless. The comment
credited the Zod bounds with covering the gap; they bound what gets
committed, not what gets read.

`readCappedJson()` counts bytes as they arrive and cancels the stream the
moment the count crosses, surfacing as a 413 rather than the old blanket
400. Six tests, every one of them on a chunked body with no
`content-length` — the exact shape the old check conceded. One asserts
the producer is never drained: offered 100 chunks of 64 KB, it is asked
for fewer than ten.

### 3. S4, the limiter nobody was reading

`check:config` mirrored `PROPOSAL_LIMITER` only.
`REGISTRATION_LIMIT_PERIOD_S` carried the identical obligation and had no
reader; both are 60 today, so no drift was live to find. Both limiters
now come off one `LIMITER_MIRRORS` table that `scripts/check-config.ts`
drives its source extraction from, so adding a limiter is adding its
check.

The lint also never asserted Cloudflare's `period ∈ {10, 60}`, meaning a
matched pair at 30 passed CI and failed at deploy. That is now its own
finding, separate from the mirror, because it holds whether or not the
two sides agree. Verified against the real `wrangler.jsonc` by planting
registration drift and then an off-platform 30.

### 4. S5 and S6

The 500 handler returned `error.message`, justified in a comment by
"every caller is authenticated". `route()` also serves anonymous `/mcp`
reads, `/api/whoami`, markdown negotiation and every static asset, so the
justification never described the reachable set. It now returns a fixed
message; the structured code, which is the part a client can act on,
stays.

`public/_headers` gains `nosniff`, `Referrer-Policy` and HSTS on `/*`.
CSP was deliberately left to its own probe, as the plan allowed: the
static export inlines its bootstrap scripts, so a policy worth having
needs per-build hashes, and getting it wrong breaks the page rather than
logging a warning.

### 5. The signing key, which turned out to be the real find

Inverting `publish-registry.sh` to prefer the keychain was meant to be
the cheap item. Storing the key surfaced two facts instead.

The keychain entry under `mcp-publisher-untype` holds an 8-character
value, not a 96-hex P-384 scalar, and `key.pem` is absent from the
project tree and the top three levels of `~`. So the signing key is in
neither place the script looks. That is unresolved and belongs to the
operator; rotation via the apex TXT record is the documented path if it
is genuinely gone.

Two commits past the plan came directly out of that. A shape guard, since
making the keychain outrank the PEM means anything under that service
name wins and `add-generic-password` stores a typo without complaint — a
malformed entry is now skipped with a warning rather than reaching
`login` as an opaque failure. And the DNS check the PEM branch always had
and the keychain branch never did, now that the keychain is the primary
source: node's `createECDH` reconstructs the public point from the stored
scalar, over stdin rather than as an argument for the `ps` reason the
file's own header gives.

The derivation was checked against a throwaway P-384 key, agreeing with
the openssl path the PEM branch uses and rejecting a perturbed scalar.
All three keychain paths were then exercised against the committed code:
the live 8-character entry (skipped with the warning), a valid matching
key (accepted), and a valid non-matching one (fatal before the registry
is contacted).

## Decisions worth remembering

- **The byte cap lives in `src/lib/proposals.ts`, not the Worker.**
  vitest's include is `src/**/*.test.ts`, so a `worker/` home would have
  shipped the fix untested, and chunk 6 is what would change that. Beside
  `LIMITS` is also where the other proposal bounds already are. This is a
  departure from the chunk's wording and is recorded in the plan.
- **Escaping `<` alone is the fix, and the comment says why.** The
  temptation is to escape `&` and `>` as well, which looks more thorough
  and is dead code: script content is raw text, not entity-decoded. The
  reasoning is written down so a later reader does not add them back as a
  precaution.
- **The platform-period check is separate from the mirror.** A matched
  pair at 30 is still illegal, so folding it into the mismatch branch
  would have hidden the case that only fails at deploy.
- **A malformed keychain entry falls through rather than failing.**
  Reordering made the keychain authoritative, which turns any junk under
  that service name into an outage. Falling through to the PEM costs
  nothing when the entry is good.
- **The keychain DNS check warns without node instead of blocking.** The
  check buys an early clear message; `login` still rejects a wrong key,
  so failing closed would convert a missing tool into an outage. Same
  reasoning the prose gate uses for a missing prose-mint.
- **Faults were planted before fixes were believed.** Continues the
  practice from sessions 45, 46, 48 and 53. Two of the six items looked
  obviously correct and were still checked this way.
