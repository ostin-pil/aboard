## Context

Slice 2 of `plans/proposed-direction-2026-07.md`: elevate the MCP server from
local stdio to a remote endpoint any client can connect to. The plan was
written on 2026-07-22 and rested on one timing claim, that "the 2026-07-28 MCP
spec goes stateless, making remote servers trivially hostable". Checking that
claim before writing code is what shaped the session: the date is real, but it
is a **release candidate that goes final on the 28th**, two days after this
session, and it is a breaking revision. That turned a one-shape build into a
two-shape one.

## What happened

### 1. The spec check, before any code

The plan's premise needed verifying because the endpoint's whole shape depends
on it. What the published spec actually says:

- **Legacy** (`2025-11-25` and earlier): `initialize` handshake, optional
  `Mcp-Session-Id`, a GET SSE stream, servers may send their own JSON-RPC
  requests. This is what every shipping client speaks today.
- **Modern** (`2026-07-28`, RC locked 2026-05-21, final 2026-07-28): no
  handshake at all. Every request carries its version in
  `_meta.io.modelcontextprotocol/protocolVersion`, mirrored into required
  `MCP-Protocol-Version` / `Mcp-Method` / `Mcp-Name` headers that the server
  MUST validate against the body. Sessions, the GET stream, and server-initiated
  requests are all removed; `server/discover` is required.

The spec calls a server that answers both **dual-era** and explicitly permits
serving them concurrently on one endpoint, selecting on how the client opens.
That is what shipped, because the alternative was choosing between "works with
clients that exist" and "works in two days".

Dual-era is close to free here, and the reason is worth keeping: aboard's server
is stateless by nature, so it never used the session the new revision removes,
and never needs the multi-round-trip input the new revision adds. The cost is
confined to header validation and two error codes.

### 2. The endpoint (`a6f5bf4`)

`POST /mcp`, split the way the Worker already splits: pure core in
`src/lib/mcp/` (`protocol.ts` decides what a message means and what it should
produce; `tools.ts` holds the catalogue), thin IO shell in `worker/mcp.ts`. Only
the shell touches the assets binding or GitHub.

Nine tools. The five read tools project the published JSON-LD through the
`ASSETS` binding. The four `propose_*` tools go through the write path that has
been live since session 20 — which required splitting `handleProposal` into an
HTTP shell plus `runProposal`, so `/api/proposals` and `/mcp` share one
definition of who may write. A second copy of the auth or rate-limit check is
exactly how those two drift apart.

`runProposal` takes the envelope as a thunk rather than a value. That looks
fussy and is not: it preserves the shipped ordering, where an unauthenticated
caller is turned away *before* its body is read.

### 3. Tool schemas are derived, not duplicated

The plan recommended hand-writing the tool input schemas as JSON Schema in the
Worker, accepting "small duplication" to avoid coupling the Worker build to the
sibling stdio package. Zod 4's `z.toJSONSchema(..., { io: "input" })` over the
existing `ClaimPayload`/`EdgePayload`/`PredictionPayload`/`DossierPayload`
avoids both the coupling *and* the duplication: the Worker already imports
`src/lib/proposals.ts`, and `io: "input"` renders exactly what the validator
accepts, including which fields are optional because they carry a default.

What an agent is told and what the validator enforces now cannot drift, which
is the same property `content/` gave editorial prose in session 29.

### 4. The server card, and a spec that moved (`5c38ede`, `c99bfd0`)

The plan named `/.well-known/mcp/server-card.json` "per SEP-1649/2127". That
path is not settled: SEP-2127 is still **open**, and it has since renamed its
own file to `ai-catalog.json`. What *is* settled is the registry's
`server.schema.json`, which has a published schema and a validator behind it.

So the card is written to the registry schema and served at both
`/.well-known/mcp.json` and the SEP-era `/.well-known/mcp/server-card.json`,
rather than inventing a shape for the second path. Two static files, one
document.

Two corrections landed later, while working out how registry publication
actually happens: the schema pointer was superseded (`2025-10-17` to
`2025-12-11`, same shape), and the name became `me.untype/aboard`. The name
matters — publishing under DNS verification of `untype.me` grants the
`me.untype/*` namespace, and the card's name has to sit inside it.

### 5. Deployed and verified in production

`wrangler deploy`, then the same 55 checks against `https://aboard.untype.me`.
Then the check that actually counts, which curl cannot make: a real
`@modelcontextprotocol/sdk` 1.29.0 client over Streamable HTTP connects,
negotiates, lists nine tools, calls read tools against live data, and gets a
correct 401-derived tool error for a write without a token.

One production-only surprise: the first run reported `DELETE /mcp` as 404 where
local returned 405. Re-checking a minute later returned our Worker's 405 with
the right `Allow` header. It was deploy propagation, caught mid-rollout, not a
bug — but it means a smoke run immediately after `wrangler deploy` can lie.

## Decisions worth remembering

- **Verify a plan's timing claims before building on them.** The premise here
  was two days from being true and was breaking. Nothing else about the session
  would have been wrong, exactly — it would just have shipped an endpoint that
  needed rewriting within the week.
- **Dual-era is cheap only because the server is stateless.** The mechanisms
  `2026-07-28` removes are ones aboard never used. That is a fact about this
  server, not a general claim about MCP; a session-based server would face a
  real migration.
- **Derive tool schemas from the canonical validator.** A hand-written JSON
  Schema is a second definition of what a valid proposal is. `io: "input"` is
  the flag that makes the rendering honest about defaults.
- **One write path, two doors.** Splitting `runProposal` out was the whole
  integration: MCP writes inherit auth, rate limiting, validation, and the
  PR-only posture by construction rather than by parallel implementation.
- **An unsettled spec is a reason to serve the settled shape at both paths**,
  not to invent a shape. SEP-2127 renamed its own file while open; the registry
  schema did not move.
- **Deploy propagation can produce a false failure.** Give the edge a moment
  before believing a post-deploy smoke run.
- **The canonical-URL guard earns its keep.** It caught a hardcoded origin in
  `SERVER_INFO` that type-checking and the build both passed. The fix imports
  `CANONICAL_ORIGIN` rather than calling `siteBaseUrl()`, because the Worker has
  no `process.env` to read.

### The yardstick scan

`isitagentready.com/aboard.untype.me`, the first scan since the endpoint
shipped. Category standing: Discoverability 3/4, Content 1/1, Bot Access
Control 2/2, API/Auth/MCP/Skill Discovery 2/7.

**MCP Server Card passes**, which was the target. The result worth keeping is
not the pass, though — it is how the scanner got there. It did not stop at
fetching the file. It deep-probed the endpoint:

```
POST /mcp   mcp-protocol-version: 2025-11-25
MCP initialize succeeded (protocol 2025-11-25)
tools/list returned 9 tool(s)
```

The scanner opened with the **legacy** handshake. Built modern-only against
`2026-07-28` — which is what the slice-2 brief described, and what the
"stateless spec" framing pulled toward — this check fails today, and keeps
failing until the client population migrates. The dual-era decision was load
bearing within twenty-four hours of being made, and it was an outside party
that exercised it.

The two-path card hedge also proved to be hedging against something real. The
scanner probed three paths in order: `/.well-known/mcp/server-card.json` (ours,
found), `/.well-known/mcp/server-cards.json` (plural — 404, a fourth spelling
nobody has mentioned), then `/.well-known/mcp.json` (ours, found). Either of
ours alone would have passed this particular scanner; the point is that four
spellings are in circulation for one file whose SEP is still open.

### The OAuth question, resolved

Sessions 29 and 30 both carried the same unresolved item: *the OAuth-shaped API
checks may be not-applicable given aboard's static agent tokens; worth deciding
before chasing that subscore.*

Decided: **they are applicable.** Three independent lines arrived at OAuth
within the same hour, which is what makes this a decision rather than a
preference.

1. Two of the five failures in the weakest scan category are OAuth-shaped
   (OIDC discovery, and Protected Resource metadata). One workstream clears
   both.
2. Smithery's auth model is OAuth. A Smithery user can see the four `propose_*`
   tools and cannot call them, because a static bearer token is not something
   their gateway can obtain.
3. MCP's own auth story is built on RFC 9728: a 401 carrying `WWW-Authenticate`
   that points at `/.well-known/oauth-protected-resource`. Our 401 carries no
   such header, so an agent that wants to authenticate has nothing to follow.

The subscore was never the argument. Two real consumers and the protocol's own
spec are.

### Smithery: no connection parameters

The publish flow asks for connection settings — parameters a user supplies to
connect. Answer: none, skip the step.

The reasoning is a security one and belongs here. Smithery Gateway proxies to
the upstream server, so a token declared as a connection parameter transits a
third party. These tokens open pull requests against the repository, and
`worker/README.md` already says not to hand one to something you would not hand
the repo to. Anyone holding a token can point a client straight at
`https://aboard.untype.me/mcp` and skip the gateway, so the parameter would buy
access nobody gains and route a credential through a party who does not need
it. Read tools need no credential, and the write tools already fail with a
structured, self-documenting 401.

### Deliberately not done

Three failing scan checks are being declined rather than deferred, and the
reason is the same for the first one as the project's own research gives:

- **Agent Skills index.** aboard has no skills. Publishing an index to satisfy
  a checker is the "schema without consumers" failure `research/reflection-2026-07.md`
  names as the AIF lesson. Declining it applies the project's rule.
- **WebMCP.** Browser-only, thin adoption, and its tools would restate `/mcp`.
- **`auth.md`.** Honest and cheap — the tokens really are manually issued — but
  a low-adoption convention. Worth folding into the OAuth work, not chasing
  alone.

**DNS-AID** is the one cheap remaining score (SVCB records in a Cloudflare zone
already under control, taking Discoverability to 4/4); the draft also asks for
DNSSEC on the discovery zone, which is the part that is not trivial.

### Revised next slice

`OAuth 2.1 + PKCE for /mcp`, carrying the RFC 9728 Protected Resource metadata
and the `WWW-Authenticate` header with it, and picking up `/auth.md` on the way.
That closes two scan checks, unblocks Smithery write access, and aligns the
endpoint with the MCP auth spec. It is a design job with real decisions in it
(who issues tokens, whether existing static tokens keep working), not a
subscore chase — which is why it earns its own session rather than riding one.
