## Context

Started as a complaint about one bad line of UX at session start (a
`lifecycle-kit` hook nagging about a missing manifest in a repo that had never
adopted the kit). Fixing that properly turned into a plugin fix, two rescues of
stranded work, aboard's adoption of the kit, and then the first forward slice of
`plans/repo-hardening.md`.

The through-line worth naming: **every piece of lost work found today was lost
the same way** — a session finished, committed, and then ended without running
its finalize step. That is exactly the failure the kit's one-PR-per-session
invariant exists to prevent, and it is the argument for both the adoption and
for CI.

## What happened

### 1. lifecycle-kit: the hook nagged every repo on the machine (claude-plugins PR #21)

The kit is user-scoped, so its `SessionStart` hook runs in every git repo. It
treated a missing `.claude/lifecycle-manifest.md` as a misconfiguration — but
that is just "this repo has not adopted the kit", which is the resting state of
most repos. The warning fired as pure noise, and because the hook emits
`additionalContext` as well as `systemMessage`, it landed in the model's context
too, inviting it to create a manifest nobody asked for.

The hook now validates only *adopted* projects; a missing manifest is silence.
The six skills raise the missing-manifest message themselves at the point of
use, where the intent is unambiguous. Also fixed: the message named a path
relative to nothing (`lifecycle-kit/lifecycle-manifest.template.md`), and
`emit()` did no JSON escaping, so a manifest with a quoted `remote:` value would
have produced malformed JSON.

A second commit on that PR fixed a defect in the first: the new skill text used
`${CLAUDE_PLUGIN_ROOT}`, which the kit's own README documents as *not* reliably
expanding in a skill body (only in hooks) — reintroducing the very
unactionable-path bug being fixed.

### 5. repo-hardening §3 — referential integrity (`17abb87`)

The Zod schemas validate each file in isolation, so cross-file breakage loaded
silently. New `src/lib/data/integrity.ts` checks the whole graph after every file
parses: edge `fromId`/`toId`, forecast and dossier `attachedToClaimId`, claim
`analyses[]` references, orphaned analyses, duplicate ids across domains, and
`domain` strings against the directories actually present under `data/`. All
violations are collected before throwing, so bad data reports in one pass.

Closed the hole next door: `loadEdges` returned `[]` on a non-array edges file,
hiding a malformed one. It now throws.

Current `data/` passes clean. Verified the check *fires* by building with a
deliberately dangling `toId`: the build fails and names the edge and the file.

### 6. repo-hardening §2 — CI (`3330f60`)

`.github/workflows/ci.yml` on push + PR: install, type-check, build, then serve
the static export and validate `/api/graph` and one `/api/claims/<id>` against
`public/schema/v0.json`. The build step is the real data gate — Zod plus the new
integrity checks — so malformed data fails CI by construction. That is the prereq
`plans/mcp-write-path.md` depends on.

Every step was run locally before committing.

## Decisions worth remembering

- **The build is the data gate.** Malformed or dangling `data/` cannot merge,
  because the Zod loader plus integrity checks run inside `npm run build`. No
  separate validation script to forget to run.
- **CI builds with `SITE_URL` set, and that is papering over a real
  contradiction.** Without it, the site emits relative IRIs, and
  `public/schema/v0.json` requires `format: "uri"` (absolute) — so a default
  build produces JSON-LD that fails our own published spec. CI validates the
  artifact the way a deploy builds it, which is honest, but the underlying
  disagreement needs a decision. Written up in `knowledge/issues.md`.
- **Lint is non-blocking, deliberately and temporarily.** 5 pre-existing React
  Compiler errors would have made CI red on arrival. A permanently non-blocking
  lint step is one everyone learns to ignore, so it is tracked as an issue with
  an explicit close condition.
- **A worktree is not a PR.** Two separate pieces of finished work were stranded
  today by sessions that ended without finalizing.
