## What happened

### 1. The registry validates the npm side, and nothing here could see it

The refusal named the field:

```
NPM package 'aboard-mcp-server' is missing required 'mcpName' field.
Add this to your package.json: "mcpName": "me.untype/aboard"
```

`mcpName` is the registry's ownership proof for an npm package. It
fetches the tarball's `package.json` and requires that field to equal
the card's `name`, so a card cannot advertise a package its author does
not control. DNS verification proves the `me.untype/*` namespace and
says nothing about who owns a name on npm, so the two checks are
independent and both have to pass.

Everything upstream of that had passed: the local card matched
production, `mcp-publisher validate` reported the card valid against the
published schema, the TXT record and the keychain key agreed, and login
succeeded. The failure was atomic; `--verify` afterwards showed the
entry still at `0.1.0` with no `packages` array, so nothing needed
undoing.

The cost was a second npm release rather than an edit, because the field
has to be in the *published* package and npm will not overwrite a
version. So `mcp-server` moves to `0.1.1` with `mcpName`, and both
cards' `packages[0].version` follows it. The card's own `version` stays
`0.1.1`, since the registry never accepted it and the number is still
free.

Nothing in the repo could have caught this. `mcp-publisher validate`
reads the card against the JSON Schema and never opens `package.json`;
npm accepts any extra key without comment; `npm pack --dry-run` displays
an absent field exactly as it displays a present one, which is to say
not at all. The gap was that no check related the two files.
`server-card.test.ts` now asserts `mcpName` equals the card's `name`,
verified by planting a mismatch.

### 2. Glama was right, and the endpoint was wrong

Glama listed aboard as unhealthy at
`glama.ai/mcp/connectors/me.untype/aboard`. Two things about that were
not what the plan document had assumed. No submission had been made:
Glama sourced the listing from the official MCP registry, which is an
argument for the registry entry that section 0 of the runbook had been
treating as merely incomplete. And it health-checks the `streamable-http`
remote rather than the npm package, so the badge was about
`worker/mcp.ts` and not about anything session 67 shipped.

The endpoint was not down. Anonymous `POST initialize` returned 200 with
a valid result, and `tools/list` returned all nine tools. Probing it the
way a browser-shaped client does found the fault immediately:

```
POST    Origin: https://glama.ai         -> 403 "Origin not allowed."
OPTIONS Origin: https://glama.ai         -> 403
POST    Origin: https://aboard.untype.me -> 200
```

`isAllowedOrigin` allowed same-origin and loopback and refused every
other origin, as a DNS-rebinding guard. Its own doc comment carried the
premise that agent clients "call server-side and send none at all", and
one real directory falsified it. The next directory would have hit the
same wall.

Past the premise, the guard protected nothing here. DNS rebinding is a
threat to a server bound to loopback, where the browser is the only
reachable path and the server trusts its network position. This endpoint
is public over HTTPS, reads no cookie anywhere in the Worker, and gates
all four write tools on an `Authorization: Bearer` credential a browser
never attaches ambiently cross-origin. That last part was verified
rather than assumed: an unauthenticated `propose_claim` against the live
endpoint returns 401. So a hostile page reaching `/mcp` gets what
`/api/graph` already serves it CORS-open, and 401 on anything that
writes.

The check is now well-formedness only, which is the rule the spec
actually asks for. `corsHeaders` echoes the origin, which stays safe for
the same reason, and the worker test now pins the absence of
`access-control-allow-credentials` so that reason is checked rather than
merely commented.

### 3. The test that was pinning the defect

`worker/mcp.test.ts` already exercised this path. It asserted 403 for a
foreign origin, under the name "refuses a foreign Origin before anything
else". The suite was not blind to the behaviour; it was holding it in
place as intended.

That is the part worth carrying forward. A test encodes a policy, and it
cannot tell you the policy is wrong. Every command in the gate passed
throughout, and the endpoint answered `curl` correctly the whole time,
because `curl` sends no `Origin` unless told to. What found it was
probing the way the reporting client does, including `OPTIONS`: a
preflight refusal is invisible to any tool that only ever sends the real
request.

### 4. mcp.so, dropped

The operator found no free submission path and declined to pay. Recorded
in the runbook as a decision with its reasoning rather than left as a
standing to-do, so it is not re-evaluated on every read.

The argument is that a paid slot competes with three free channels that
are already covered or in flight: the official registry, which is what
fed Glama the listing without a submission at all; awesome-mcp-servers,
which is a pull request; and Glama itself. Worth revisiting only if the
chunk 4 instrumentation ever shows mcp.so as a meaningful referrer for
comparable servers.

## Decisions worth remembering

- **A directory's health badge can be a bug report.** The instinct was
  to treat "unhealthy" as a listing problem to be worked around. It was
  a defect in `worker/mcp.ts` that no local check could see, and the
  badge was the only thing reporting it.
- **A passing test can be the thing holding a defect in place.** The
  403 was asserted deliberately, with a descriptive name. Reviewing the
  policy rather than the coverage is what changed it.
- **Probe the way the reporting client does.** `curl` sends no `Origin`,
  so every manual check had been exercising a different code path than
  the one failing. Sending the header, and checking `OPTIONS` as well as
  `POST`, found it in one command.
- **Two independent ownership proofs, one for each namespace.** DNS
  proves `me.untype/*`; `mcpName` proves the npm name. Neither implies
  the other, and the registry requires both. Worth knowing before the
  next package is added to a card.
- **Publishing order is fixed by a check, not by preference.** The card
  cannot reach the registry before the npm package exists at the version
  it pins, and the publish script will not run before the card deploys.
