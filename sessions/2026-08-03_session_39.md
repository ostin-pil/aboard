the credential, and it was good until 2026-08-27.

### 3. `OAUTH_KV` reduced to what is in use

There is no grant-revocation endpoint to call. The metadata advertises
`revocation_endpoint: https://aboard.untype.me/oauth/token`, which is RFC
7009 and requires presenting the token being revoked; we hold no token
for the stale client. So session 37's "revoke through the endpoint" was
not actionable as written, and the choice was between building an
authenticated admin route over `revokeGrant`/`deleteClient` and deleting
the keys directly.

Deleting directly, on the evidence that it is identical here.
`revokeGrant` deletes every `token:` key under the grant and then the
grant key; the stale grant had zero `token:` keys, so the two operations
have the same effect on storage. Weighed against that, an admin route is
permanent authenticated surface on an authorization server for a
housekeeping job that recurs about twice a year.

Deleted: the stale grant and all eight client registrations. `OAUTH_KV`
now holds two keys, the live grant and its current access token. The
live connection was then refreshed from the console and still lists nine
tools, with the grant intact.

One observation worth keeping: the token key changed between two listings
taken minutes apart, expiry moving 23:01 to 23:45. That is Smithery
refreshing while the console was open, and it also explains the token
issued shortly before the session started, which had looked unexplained.

### 4. The B experiment, answered without running it

The experiment was to repoint the listing at `?auth=required` and watch
whether the nine-tool list survives an anonymous rescan, reverting if it
empties. Both halves are checkable directly.

What an anonymous caller gets, against our own endpoint:

- `POST /mcp` with `tools/list`: HTTP 200, nine tools.
- `POST /mcp?auth=required` with `tools/list`: HTTP 401, no tool list,
  `WWW-Authenticate: Bearer` with the resource metadata pointer.

What the listing scan is, from the release log on the deployed release:

    22:26:00 Connecting to MCP server...
    22:26:01 Server info retrieved. name: aboard, version: 0.1.0
    22:26:01 Querying server capabilities...
    22:26:03 Capabilities found: 9 tools.

That is an anonymous `initialize` followed by `tools/list`, because
Smithery holds no credential for a published listing. Pointing a release
at `?auth=required` therefore takes the public card from nine tools to
zero. The revert condition is not a risk to watch, it is the certain
outcome, so no release was published and the listing keeps the plain URL.

This is the arrangement session 37's decision already assumed. The
listing stays discoverable with all nine tools, and the `WRITE_AUTH_NOTE`
carried in the four write tool descriptions is what tells a gateway agent
how to authenticate. Nothing needs to change.

## Decisions worth remembering

- **`wrangler kv key list` reads local state unless told otherwise.** The
  local store is a plausible forgery of production: same namespace id,
  same key shapes, realistic expiries, no marker in the output. Pass
  `--remote` and, when a conclusion rests on it, confirm the two
  listings differ.
- **A grant record is the refresh-token credential.** The provider keeps
  no separate entry; it compares a hash against `refreshTokenId` on the
  grant. A grant that looks like stale metadata is a live credential
  until it expires.
- **Hand-deleting keys was correct here because equivalence was proved
  first.** `revokeGrant` deletes the grant's `token:` keys then the
  grant; with zero such keys the operations coincide. The enumeration is
  what licensed the shortcut, and an admin route would have been
  permanent auth-server surface for a twice-a-year chore.
- **An experiment whose revert condition is certain is not worth
  running.** The anonymous 401 and the release log settle the B question
  between them, at no cost to a live listing.
- **Smithery connections share one CIMD grant.** Per-connection
  revocation is not a thing that exists; revoking reaches every
  connection at once.
