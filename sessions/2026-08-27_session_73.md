### 2. The mojibake was a header, not a character

`robots.txt` rendered its em dashes as `â€"` in a browser. The bytes were
correct UTF-8 the whole time (`e2 80 94`), which is why `curl` showed the
file perfectly and made it look like a non-problem.

The response was `content-type: text/plain` with no charset parameter.
RFC 2046 makes an absent charset on `text/*` mean US-ASCII, so the browser
fell back to its locale default and decoded three UTF-8 bytes as three
windows-1252 characters.

Seven files were affected, not one: `robots.txt`, `llms.txt`, and the five
markdown twins. The generating Route Handlers all set `charset=utf-8` and
are correct; `output: "export"` bakes the body and discards their headers,
which is the same reason `public/_headers` has to restate CORS by hand.
That file only ever listed the extensionless routes, because those have no
content type at all otherwise. `.txt` and `.md` do infer one, which is
exactly why they were missed.

The markdown twins show the shape best, because the same content was
correct on one path and wrong on the other: `/claims/S1` with `Accept:
text/markdown` is served by the Worker, which sets the charset itself,
while `/claims/S1/index.md` comes from the assets binding and did not.

Nothing in the repo read `_headers` at all: no test, no lint, no CI step.
`src/lib/headers.test.ts` is the first reader it has ever had. It asserts a
charset on every charset-dependent content type and pins the three new
paths; both faults were planted and caught before the file was trusted.

Verified through `npx wrangler dev --local`, which serves `out/` through
the real assets binding and applies `_headers`, rather than by deploying
and hoping.

### 3. The contrast finding, and the larger fault behind it

PageSpeed reported a contrast failure and named the audit but not the
element, so the palette was measured instead of guessed. In genuine light
mode the homepage had exactly one failure: `.sep`, the `·` between meta
facts, coloured with `--line-2` at 1.49 against white. A border token used
as text.

Measuring to find it turned up the bigger one. `--dark-muted-2` was
`#78716c`, byte-identical to the light `--muted-2`. Every other token in
the dark block has a value tuned for a dark surface; this one was a
light-surface grey sitting on all three dark surfaces at 3.77, 3.59 and
3.44 against a 4.5 requirement. PageSpeed never saw it, because Lighthouse
emulates light.

Three changes: `.sep` now uses `--muted-2` in all four rules,
`--dark-muted-2` becomes `#8f8880` (the smallest move clearing AA on every
dark surface while staying dimmer than `--dark-muted`), and light
`--muted-2` goes `#78716c` to `#756e69`, since it was passing everywhere
except `--hair` at 4.40. `tokens.ts` follows the light value for the OG
cards, and `tokens.test.ts` confirmed the two languages still agree.

`src/lib/contrast.test.ts` is the gate. axe is the tool that would normally
catch this, and `color-contrast` is precisely the rule that cannot run in
jsdom, because it needs real layout and compositing. So the palette's
arithmetic is checked where it needs no browser. Both original values were
planted and caught, each naming the pair and the ratio.

The OG card's own `separator` was left alone. `tokens.ts` already records
that it has the same flaw and that correcting it re-renders every claim
card, which is a design decision on the record; it is also an image, which
no contrast audit reads.

### 4. Two false alarms, both from the same methodological error

Worth writing down because the error is easy to repeat. Scanning after
setting `data-theme` on the root, without reloading, produced light
foregrounds on dark backgrounds and made it look as though the theme
guards were broken. They are not: the root tokens were checked directly
and every one resolves correctly under a forced light theme. The graph
mounts with inline styles read at mount time, so flipping the attribute
afterwards leaves them stale. A second scan reported footer links failing
for the same reason.

Both vanished on a clean reload. Any contrast pass over this site has to
set the theme through `localStorage` (`aboard.theme`) and reload, not
toggle the attribute in place.

### 5. Deployed before landing

The operator chose to deploy from the branch and verify production before
merging, rather than the other way round. `ci.yml` has no deploy step, only
the Worker dry-run, so a merge alone would have left both user-visible

resolving to `#756e69` in light and `#8f8880` in dark.

## Decisions worth remembering

- **A correct file can still be served wrong.** The mojibake had nothing
  to do with the bytes, and every tool that reads bytes said the file was
  fine. `curl` without `-I` actively hid it. When a rendering fault has no
  source to blame, read the response headers before re-reading the file.
- **`output: "export"` discards Route Handler headers.** Any header a
  handler sets has to be restated in `_headers`, and the repo already knew
  this for CORS without generalising it. The next static asset with a
  header requirement will hit the same wall.
- **Cover the case that looks already handled.** `_headers` skipped `.txt`
  and `.md` precisely because they infer a content type. The extensionless
  routes got attention because their failure was total; these failed
  partially, which is quieter and lasted longer.
- **Find the element before choosing the fix.** PageSpeed named an audit,
  not a selector. Measuring the palette found both the reported defect and
  a worse unreported one in the other theme.
- **A theme scan without a reload is not a theme scan.** Two separate false
  alarms came from flipping `data-theme` post-mount. Both were checked
  before being reported, which is the only reason neither reached a commit.
- **Deploy order is a real choice when CI does not deploy.** Merging would
  have recorded two fixes as done while the live site kept serving both
  defects.
