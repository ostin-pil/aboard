## Context

`plans/repo-hardening.md` §4 and the open `SITE_URL` issue in

## What happened

### 1. The vocab IRI is real (`23d61d2`)

`https://aboard.example/vocab/` → `https://aboard.untype.me/vocab/`, and the
schema's `$id` with it. Per CLAUDE.md, `public/schema/v0.json` and
`research/schema.md` moved in the same commit as `jsonld.ts`.

The vocab stays a **literal** in `jsonld.ts` rather than being derived from
`siteBaseUrl()`. That is deliberate: a vocabulary IRI is a stable public
identifier, embedded in every claim published and in any consumer that caches
the context. A preview deploy or a localhost build must not mint a different
vocabulary just because its origin differs.

### 2. The relative-IRI contradiction is fixed, not worked around

`siteBaseUrl()` returned `""` when `SITE_URL` was unset, which emitted relative
IRIs (`/claims/L1`). But `public/schema/v0.json` requires `"format": "uri"` on
every `@id` — absolute. So a plain `npm run build` produced JSON-LD that failed
**our own published schema**. Session 15 papered over this by having CI set
`SITE_URL`.

`siteBaseUrl()` now defaults to the canonical origin, with `SITE_URL` still
overriding for previews and localhost. A default build now validates clean.

**CI's `SITE_URL` crutch was removed in the same commit.** That is the point: CI
now exercises the default path a contributor actually gets. Leaving the env var
set would hide a regression in precisely the thing that was broken.

The schema was **not** relaxed to `uri-reference`. Absolute `@id`s are the right
contract for a graph whose entire premise is that agents can dereference it.

### 3. Swept the five PLACEHOLDER comments

`// PLACEHOLDER: revise after audience decision in research/vision.md` in the OG
image and detail routes. The audience decision *was* made in `vision.md` (both
human and agent), and the copy already reflects it — so the comments were stale,
not pending. Deleted; copy untouched.

## Decisions worth remembering

- **The vocab IRI is a literal, not a derived value.** Deriving it from the site
  origin would mean a preview deploy silently publishes a different vocabulary.
  It is an identifier, not a URL to the running app.
- **Fix the default, do not configure around it.** The tempting fix was to keep
  `SITE_URL` set everywhere it matters. That leaves a loaded gun: any build that
  forgets the env var emits spec-violating output. Making the *default* correct
  and then removing the env var from CI means the broken path no longer exists.
- **`aboard.untype.me` is not yet wired up.** See below — this is a maintainer
  action, not a code change.
