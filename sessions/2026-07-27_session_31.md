# Session 31 — 2026-07-27

Branch: `feature/session-31-mcp-oauth` (branch-only, primary checkout).
Opened against session 30's revised next slice.

## Context

Session 30 ended by naming OAuth 2.1 + PKCE for `/mcp` as the next slice, on
three converging grounds: two of the five failures in the weakest yardstick
category are OAuth-shaped, Smithery's auth model is OAuth so a Smithery user
can list the write tools but not call them, and MCP's own auth story is built
on RFC 9728 while our 401 carried no `WWW-Authenticate` for an agent to follow.

The session was asked for the design as a written plan first, then the build.
Both landed.

## What happened

### 1. The plan, and three premises that did not survive checking

`plans/mcp-oauth.md`, written against the published spec on the day before the
`2026-07-28` revision went final. Session 30's lesson was that a plan's timing
and spec claims get verified before they are built on, and applying it changed
the plan three times.

**Protected Resource Metadata cannot ship ahead of an authorization server.**
The session-start briefing offered exactly this as a cheap first slice: ship the
metadata document and the `WWW-Authenticate` header, defer the issuance
question. It does not hold. MCP makes `authorization_servers` a required field
with at least one real entry, so the document cannot be written until something
issues tokens. The metadata and the issuer ship together.

**GitHub cannot be the authorization server, though it can be the identity
provider.** This looked viable, and more so after finding that GitHub now
publishes RFC 8414 metadata at
`https://github.com/.well-known/oauth-authorization-server/login/oauth`. It
fails on two independent grounds. GitHub supports neither Dynamic Client
Registration nor Client ID Metadata Documents, so an arbitrary MCP client has
no way to obtain a `client_id`, and pre-registering every client by hand is not
a model. And GitHub has no resource indicators, so its tokens are issued for a
GitHub OAuth App rather than for `https://aboard.untype.me/mcp`; accepting one
is the audience-validation failure the spec forbids with a MUST.

**aboard becomes an authorization server, and that costs statelessness.**
`wrangler.jsonc` recorded that `/mcp` needs no binding. Token issuance needs
somewhere to keep clients, codes and grants. The comment was corrected in the
same commit that added the KV binding. The MCP protocol core and every read
tool stay stateless, and an anonymous read still touches no storage.

### 2. The step-0 gate, answered by reading the source

`@cloudflare/workers-oauth-provider` fits on every axis except one that the
README does not address: whether it rejects unauthenticated requests to an
`apiRoute` before the handler runs. It does, at `handleApiRequest`, on a missing
`Authorization` header. So `/mcp` cannot be an `apiRoute` without breaking
anonymous reads.

It does not have to be one. The provider handles the metadata, token and
registration endpoints first, checks `isApiRequest` second, and only then falls
through to the default handler with `env.OAUTH_PROVIDER` injected. `/mcp` stays
on the default handler and validates tokens itself through `unwrapToken`. The
constructor still demands some API route, so `GET /api/whoami` became one: an
endpoint an agent wants anyway, to check what a credential resolves to before
spending a write finding out.

A second check earned its keep. The spike read the repository's `main`; the
installed package is `0.8.2`, where `TokenSummary.scope` is already a `string[]`
rather than the space-delimited string `main` implies. Reading the published
build caught it before it became a runtime bug.

### 3. The shape the spec does not cover

`/mcp` is half public and stays that way, so the challenge is a per-call
decision rather than a per-endpoint one. `tools/list` answers everyone and
lists all nine tools, because a client that cannot see the write tools has no
reason to authenticate. Calling a `propose_*` tool without a credential is what
draws the 401.

That also draws a precise line through session 30's design. Proposal rejections
stay tool-level errors with field paths attached, because a model can act on
those. A missing or invalid credential becomes an HTTP status code, because it
is the client and not the model that has to act on it, and a 401 carrying
`WWW-Authenticate` is what starts an OAuth flow.

### 4. What shipped (`646670b`, `5d2021d`, `e3e8368`, `46e516f`)

Pure decisions in `src/lib/mcp/auth.ts` and `src/lib/mcp/consent.ts`; IO in
`worker/oauth.ts`; the same split as everything else in this Worker.

The authorization server wraps aboard rather than the other way round, because
it has to see a request before the site does. Consent is signed rather than
stored: the in-flight authorization rides in the `state` parameter under HMAC,
so the client and redirect URI a human is shown are the ones the token is
issued against, and the server keeps no session across the trip to GitHub.

Identity resolution became two-source behind one decision function. Static
agent tokens keep working unchanged. OAuth tokens resolve through `unwrapToken`
with the audience checked against the canonical resource URI, because the
library binds the RFC 8707 `resource` but does not validate it at the resource
server, which is correct: that is the resource server's job.

Three things went beyond the plan, each because checking turned up something
the plan had guessed at.

- **CIMD is on.** The plan listed Client ID Metadata Documents as a follow-up.
  A `wrangler dev` warning revealed the library supports them behind the
  `global_fetch_strictly_public` compatibility flag plus an option. Since the
  `2026-07-28` revision prefers CIMD and deprecates the DCR it replaces,
  enabling it now was the cheaper decision. DCR stays on for older clients.
- **RFC 9207 `iss` is emitted.** The library does not, and the spec makes it a
  SHOULD today and a future MUST. Our own handler performs the final redirect,
  so appending it was three lines. We deliberately do not advertise
  `authorization_response_iss_parameter_supported`, because that document is the
  library's to generate; silence plus a present `iss` is the row of the spec's
  compatibility table that still validates.
- **Endpoints are pinned to the canonical origin.** The library resolves a bare
  path against the inbound request, which made `issuer` a function of how the
  server was reached and produced an `http` issuer under `wrangler dev`. Every
  authorization server endpoint MUST be https, and published metadata should not
  vary by route.

`/auth.md` also landed. Session 30 declined to chase it alone as a low-adoption
convention while noting it was honest and cheap; the occasion to add it is the
work that makes it true.

### The end-to-end run, and the two bugs only it could find

Driven through a real browser against production, with a loopback listener
catching the code. It found two bugs, both invisible to every other layer.

**A colon in the grant subject broke every token the server issued.** The
provider packs the subject into every authorization code and access token as
`${userId}:${grantId}:${random}` and parses them back with `split(":")`,
requiring exactly three parts. The subject was `github:<id>`, so every code had
four parts and the token endpoint answered `invalid_grant` with "Invalid
authorization code format". No OAuth credential could ever have worked. Unit
tests passed, and so did every production check up to the redirect, because
nothing before the code exchange touches the token format. Fixed by
`oauthSubject`, with a regression test asserting the packed token still splits
into three.

**`/api/whoami` could not be called by any token this server issues.** It was
the `apiRoute` that satisfies the provider's constructor, chosen on the
reasoning that it was an endpoint an agent wants anyway. That reasoning was
wrong: the provider validates a token's audience against the *request path*,
computing `${protocol}//${host}${pathname}`, and our tokens are audience-bound
to `/mcp` because that is the resource an MCP client asks for. The endpoint was
reachable only by a token no client would ever request. It now lives in the
site handler behind the same resolver that guards `/mcp`, and the constructor's
requirement is met by an unadvertised placeholder.

After both fixes, verified against production:

- aboard's consent page renders correctly, and both requirements that are spec
  text rather than taste are visibly working: the redirect host
  (`127.0.0.1:8976`) is displayed, and the loopback warning fires.
- The code carries `state` round-tripped and `iss=https://aboard.untype.me`,
  the RFC 9207 parameter the library omits and this session added by hand.
- The token exchange returns `scope: aboard:propose`, `resource:
  https://aboard.untype.me/mcp`, one-hour expiry, and a refresh token.
- `/api/whoami` with that token returns `operator: ostin-pil` and the
  registered client name. That is the provenance upgrade proven end to end: a
  verified GitHub login rather than a string typed into a table.
- The token clears auth on a write tool and reaches validation, returning a
  field-level tool error rather than a 401. Anonymous reads stay 200, anonymous
  writes stay 401.

## Decisions worth remembering

- **Verify a published build, not the repository's main branch.** The spike read
  `main` and would have shipped a wrong assumption about `scope`'s type. The
  installed artifact is the one that runs.
- **A dangling discovery pointer is worse than none.** With no authorization
  server configured the 401 still fires but omits `resource_metadata` and
  `scope`, because a conforming client fetches that URL, fails, and has nothing
  to fall back on. This is what lets the slice deploy in stages.
- **A local observation can lie, again.** The `WWW-Authenticate` header showed
  `http://localhost:8799` under `wrangler dev` while the code builds it from
  `CANONICAL_ORIGIN`. Wrangler rewrites absolute URLs in response headers to
  match the inbound request; the body documents were untouched and the unit test
  asserting the canonical value passed, and production later confirmed the
  canonical URL. Session 30 caught deploy propagation faking a failure; this is
  the same genus.
- **Propagation fails intermittently, not cleanly, and one success proves
  nothing.** Session 30 recorded that a smoke run straight after `wrangler
  deploy` can lie. The sharper version: a new path alternated 404 and 200 for
  about ninety seconds while old isolates drained, so a single passing probe was
  not evidence. What settled it was waiting for a streak of consecutive
  successes. Any post-deploy gate on a path that did not previously exist should
  require a streak rather than a hit.
- **Refuse at consent, not at the token endpoint.** A refused login should never
  reach a code exchange, and the person deserves to be told why while they are
  still looking at a page. The allowlist is checked again at issuance, because a
  page can sit open while the list tightens.
- **The provenance upgrade is the point, not the subscore.** `operator` becomes
  a verified GitHub login instead of a string a human typed into a table. The
  two failing scan checks are a side effect. Confirmed live: `/api/whoami`
  returns `operator: ostin-pil` from a token, with no table involved.
- **An end-to-end run is not a formality.** Both bugs it found were total
  failures of the feature, both survived a full unit suite and every
  production check that stops short of exchanging a code, and neither was
  visible from the outside until a real credential was minted. The lesson is
  narrower than "test more": a layer you have only exercised in halves is
  untested, however many halves pass.
- **The GitHub login is identity, not authority.** Pull requests are still
  opened by aboard's own PAT, and `read:user` is the only scope asked of GitHub.

### Closing the registration hole

Raised while reviewing the session's own leftovers, and fixed before the
session ended.

Dynamic Client Registration is unauthenticated by design: a client that has
never met this server still has to be able to obtain a `client_id`. That makes
`/oauth/register` the only unauthenticated write into `OAUTH_KV`, and it had no
brake, because `PROPOSAL_LIMITER` is keyed on proposals and never covered that
path. `REGISTRATION_LIMITER` now caps it at 5 per minute per client IP. The
brake sits in a wrapper around the provider rather than in the site handler,
because the provider answers `/oauth/register` before our own code sees the
request.

One correction to how this was first written up. Registrations were never
immortal: the library applies a 90-day `clientRegistrationTTL` when the option
is omitted, so they always self-cleaned, and the exposure was bounded rather
than unbounded. The value is now stated in our own config instead of inherited,
so a reader can see it and a future default change cannot move it silently.

Verified in production: five registrations succeed and the sixth is refused
with 429 (Cloudflare's limiter is documented as approximate and permissive, so
the exact cut-off drifts by one). Every other path is unaffected, and the token
issued earlier in the session still resolves to `operator: ostin-pil`.
