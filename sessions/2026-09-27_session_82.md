## What happened

### 1. The fix is visible, in one place rather than everywhere

Probe arrivals rose about 20% across matched nine-day windows, 1,193 a
day to 1,427. That alone would be weak: the ranges overlap and nine days
a side cannot separate a step from a trend.

The `GET` series is not weak. It ran at 23 to 41 a day for the whole
pre-fix window and stepped to 97 to 116 on 2026-09-18, the first full
day after the fix, and has stayed there. The recognised-crawler share
moved by six arrivals in nine days, which is what a fix aimed at
datacenter clients should look like.

Reads went the other way: 97 in the nine days before, 43 in the nine
after. Nothing measured here supports a story where removing the block
brought readers, and the session log should say so plainly.

### 2. The launch post's sentence reproduces exactly

350 reads over the twenty-five days to 2026-09-11, min 1, max 47, mean
14. Extended to 2026-09-26 it is 464 reads over forty days, still with
no zero day. The report offers replacement wording and deliberately does
not apply it, because that file belongs to session 78's open branch.

### 3. Sampling has started, which no document knew

`_sample_interval` reaches 10 on probe rows and 2 on read rows.
`worker/README.md` says it "will read 1 for a long time", and that
stopped being true somewhere in the last month. Every number the project
has published summed the interval, so the historical figures stand; what
changes is that they are now estimates rather than counts, and any
future query that reaches for `COUNT()` will quietly be wrong.

### 4. The Glama connector is still failing, and the rows say why

Read in the browser: Unhealthy, uptime 0.0% over 41 days, and **not
claimed**. Session 77's audit recorded it as claimed, which was about
the server listing rather than the connector. Zero per cent over
forty-one days means it has never passed, so the fault predates Bot
Fight Mode being suspected and survived it being fixed.

The correlation the `mcp_probe` counter was built for finally paid.
Glama's page shows local time, so its "last tested 12:44" is 11:44 UTC,
and that second carries three arrivals: a `POST` and a `GET` together,
both asking for `text/event-stream`. The `POST` is answered 200. The
`GET` is answered 405, by session 72's deliberate decision.

That makes the 405 the leading suspect and not a conclusion. Before the
fix that `GET` was challenged at the edge and never arrived, so the fix
bought the checker a 405 where it used to buy a 403, and both may read
as broken from the outside. The unclaimed connector is a live
alternative explanation, since the Admin tab advertises test-profile
credentials for health checks.

## Decisions worth remembering

- **A clock is a measurement too.** The first Glama correlation came
  back empty because the query window was in the future: server time was
  11:53 UTC and the page's "12:44" was local. That is session 63's trap
  wearing a different hat, and the habit that catches it is asking the
  server what time it thinks it is before trusting any window.
- **Name the instrument's blind spot before reading it.** The agent
  class `glama` has never appeared in a single row, which says nothing,
  because the classifier only matches a user agent carrying that word.
  The timestamp answered what the label could not.
- **A verification at the door is not a verification of the traffic.**
  Session 80 proved the endpoint answers a runner. Ten days of rows were
  needed to show that the audience actually changed, and to show that
  one caller it was meant to fix is still failing.
- **Do not reuse a drafted message once its premise has moved.** The
  #257 reply was correct when written and false by the time it could be
  sent. Re-read a draft against the world, not against the plan.
- **Measure the thing you can attribute.** The 20% rise in total
  arrivals is confounded; the four-fold `GET` step on the first full day
  after the fix is not, and it is the smaller, sharper claim.
