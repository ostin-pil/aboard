## What happened

### 1. Vitest, and the first test suite (`78bb9ae`)

26 tests over the two modules that are pure and dependency-free, so neither
drags in Next or `server-only`:

**`src/lib/data/integrity.ts`** — every check has a test: dangling edge
`fromId`/`toId` (including that the two ends are distinguished, and that both
report when both dangle), forecast and dossier attachment to unknown claims,
claims referencing missing analyses, orphaned analyses, duplicate ids minted in
two domains, and domains with no directory behind them.

Beyond the checks themselves, the tests pin the properties that make the errors
*usable*, which is the actual product here:

- every violation is reported in one pass, not just the first;
- the offending file is named, and for a duplicate, **both** files are;
- ordering is deterministic;
- an edge and a claim may legitimately share a bare id string — only a collision
  within one kind is a duplicate. (No false positive.)

**`src/lib/model-family.ts`** — the label mapping, case-insensitivity, the
fallback to `other` rather than throwing on an unknown provider, and the
ordering guard the module's own header calls load-bearing: `gpt-oss` is tested
before the broader tokens, because a misattributed run would make an ensemble
look more diverse than it is. That is the whole point of the family grouping,
so it is worth a test rather than a comment.

### 2. Mutation-checked, not merely run

A green suite proves nothing until it can go red. Disabling the duplicate-id
check and separately the orphan-analysis check each turned the suite red, then
both were restored. Both mutations were caught.

### 3. Wired in as a hard gate

`npm test` runs in CI as a **blocking** step, deliberately unlike lint: the
suite is green today, and a gate that is optional on day one never becomes
mandatory later. `test_commands` in `.claude/lifecycle-manifest.md` is now
`["npm test"]`, so `/lifecycle-kit:session-end` runs it too.

## Decisions worth remembering

- **Test the pure modules, not the loader.** `loader.ts` imports `server-only`
  and touches the filesystem, so unit-testing it would mean mocking the Next
  runtime. It is already covered end to end: `npm run build` runs the real
  loader over the real `data/`, and session 15 verified that a dangling
  reference actually fails the build. Vitest is therefore scoped to
  `src/**/*.test.ts` over pure logic; the build remains the integration test.
- **A suite that has never failed is not evidence.** Mutation-checking took two
  minutes and is the only reason the 26 green ticks mean anything.
- **Hard gate from day one.** The lint step's `continue-on-error` is a temporary
  concession to pre-existing debt with a written close condition. `npm test` got
  no such concession, on purpose.
