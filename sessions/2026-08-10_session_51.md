## What happened

### 1. The premise was wrong, and testable

E10 said "no deploy automation exists; `.github/workflows/` has only `ci.yml`".
The first half does not follow from the second. Every PR in this repo carries a
`Workers Builds: aboard` check, which is Cloudflare's git integration,
configured in their dashboard and therefore invisible to `ls .github/workflows`.

Testable, because session 49 had added `--edge-evidences` to `globals.css` hours
earlier. If Cloudflare deploys on merge, the token is in the deployed stylesheet:

```
11ak2079405zr.css  edge-evidences=1  edge-reduces=1
```

It is. Deploy-on-merge already exists, so the staleness window is one build
cycle rather than open-ended, and one of the audit's three options was already
done.

### 2. The consequences did not survive reading either

The audit lists three. Only one produces the failure it describes.

| Claimed consequence | What actually happens |
| --- | --- |
| merged-but-undeployed claim mints a duplicate id, 422, opaque `github_failed` | correct |
| concurrent agents mint the same id into conflicting PRs | both PRs create the same path, so the second is an add/add merge conflict GitHub shows and a human gates. Visible, not corrupting |
| merged-but-undeployed dossier slips past the overwrite refusal | correct, and the same 422: `dossierExists` comes from the stale graph and the write is a create |

And the 422 is reachable from exactly two of the four proposal kinds. Claims and
dossiers `PUT /contents` with no `sha`, which is a create. Edges and predictions
read their target file live from GitHub at `ctx.base` and commit with its `sha`,
so they never touch that path. A stale *edge* id is a real defect, but it lands
as a duplicate id inside `edges.yaml` that CI's integrity check rejects on the
PR. Different failure, different fix, left open and named rather than folded in.

### 3. Which made the choice easy

Reading ids live from GitHub would close a window measured in minutes, at the
cost of API calls on every write, and would leave the observable symptom exactly
as opaque. So the fix is the one the audit listed last, under "at minimum".

Three things were wrong with `502 github_failed`, and only the third is
cosmetic. It asserts GitHub misbehaved when GitHub refused correctly. It gives
the caller no field to branch on, so an agent cannot tell a retryable collision
from an outage. And the single action that resolves it, re-read and retry, does
not appear anywhere in the response.

### 4. The shape of the fix

`submitProposalPR` returned `{ ok: false, detail: string }`. Every one of its
four failure points collapsed into that one string, and the handlers wrapped it
in a fixed 502. It now returns a `SubmitFailure` carrying `step`, `status`,
`path`, and `intent`.

`intent` is the field that makes 422 legible. `PUT /contents` creates when `sha`
is absent and updates when it is present, and GitHub answers 422 for both a
create over an existing file and a stale `sha` on an update. Status alone cannot
separate "the id is taken" from "someone moved this file under me"; status plus
intent can.

The classifier lives in `src/lib/proposal-errors.ts` because `worker/index.ts`
exports only its default handler, so nothing in the repo can reach a function
defined there. That is the same constraint session 47 hit with A6 and answered
the same way, by moving the logic to `src/lib`.

The collision returns `409`, not `422`. The payload was valid and the id was
free when it was minted; what changed is the state of the target, which is what
409 describes. A 422 would tell the agent to fix input that has nothing wrong
with it. The body carries `id`, `path`, `retryable: true` and a per-kind
`remediation`, since "mint the next id" is wrong advice for a dossier, where a
second dossier is refused by design and there is no next id.

Everything that is not the collision keeps the previous 502 verbatim, including
its empty `extra`, so nothing already parsing that contract shifts.

## Decisions worth remembering

- **Check the premise before choosing between the remedies.** E10 offered three
  options and one was already implemented, in a place the audit could not see
  because it is configured outside the repo. A single curl against the deployed
  CSS settled it.
- **An audit's consequence list is a claim, not a finding.** Two of E10's three
  consequences did not survive reading the code: one is a visible merge
  conflict, and the third shares the first's mechanism. Fixing what was actually
  there beat fixing what was written down.
- **Distinguish the window you can close from the window that matters.** Live
  GitHub reads would close a minutes-long staleness gap and leave the failure as
  unreadable as before. The cheaper fix addressed the part a caller experiences.
- **409 over 422 when the input was never wrong.** The status code is the first
  thing an agent branches on, and 422 is an instruction to change the payload.
  Here there is nothing in the payload to change.
- **A field, not a status, is what makes an error legible.** 422 means two
  different things on `PUT /contents`. Recording `intent` at the call site is
  what lets a pure function tell them apart later.
- **Verify a Worker change in the bundle.** `tsc` reads `worker/`, but only the
  wrangler dry-run reads the config that decides what ships.
