### 2. Annotations, derived rather than written

All nine tools now publish `annotations`, and they are derived from the
existing `handler` discriminant rather than written per tool. The handler
already encodes the only thing the hints depend on, so writing them out
would be a second statement of one fact, free to drift the moment a tool
changed kind. That is the same argument session 30 used to derive input
schemas from Zod. A test asserts
`readOnlyHint === (handler.kind === "read")`, so the derivation cannot
later be replaced by literals without failing.

The hints themselves: read tools are read-only and closed-world, since
they read our own published API rather than an arbitrary URL. The four
`propose_*` tools carry `destructiveHint: false`, which is the
substantive claim in the set, because a proposal opens a pull request
that only ever adds and is never auto-merged. `idempotentHint: false`
because two identical calls open two pull requests. Destructive and
idempotent are omitted entirely on read tools rather than defaulted, the
spec being explicit that they are meaningful only when a tool is not
read-only.

### 3. Parameter descriptions, 5 of 9 to 9 of 9

The gap was exactly the four `propose_*` tools. All four read tools
already described their arguments, and `get_graph` takes none, which is
precisely the 5. The four write tools failed because their fields live in
`src/lib/proposals.ts`, which carried four `.describe()` calls across all
four payload schemas.

Fixing it there rather than in the tool layer keeps `tools.ts` deriving
from the validator, so what an agent is told and what the validator
enforces still cannot diverge. `Source` in `types.ts` was deliberately
left alone: it is shared with the data-loading path and carries the
"update `v0.json` in the same commit" obligation, so describing it is a
separate call.

### 4. Output schemas, lifted from the published spec

The spec makes this binding: a tool that declares an output schema
**MUST** return structured results conforming to it. So the schemas are
derived, and only where the shape is actually guaranteed.

`get_graph`, `get_claim` and `get_dossier` return documents
`public/schema/v0.json` already describes, so they lift
`ClaimGraphResponse`, `FullClaimResponse` and `Dossier` out of it. This
propagates a contract the project already holds the API to rather than
inventing a second description. `list_claims` and `get_forecast` return
envelopes this layer builds, so those are declared in Zod and rendered
through the same path as the input schemas. `get_forecast` is a
discriminated union rather than one shape with optional halves, because
neither branch ever omits its own fields.

Each schema carries the transitive closure of the `$defs` it needs, so a
client can validate offline. A remote `$ref` to the schema's published
`$id` would be roughly 200 bytes against 28KB and is genuinely
resolvable, but most validators will not fetch one, so it would describe
nothing to most callers. The cost is real and worth naming: `tools/list`
goes from 18.5KB to 53.3KB, fetched once per connection.

The write tools now return the proposal as structured content beside the
prose, so a model reads the pull request URL as a field rather than
parsing it out of a sentence. `merged` is a literal `false` rather than a
boolean, because the write path has no branch that merges and a boolean
would describe a state the server cannot reach. A rejected proposal stays
an `isError` result carrying the validator's field paths as text with no
`structuredContent`, which is the shape the spec's own error examples
use and the only honest answer for "this did not happen".

### 5. Conformance was proven, and proving it found a bug

Declaring a binding schema and not checking it would have been the whole
failure mode, so the declared schemas were validated under ajv against
live production documents: `/api/graph`, `/api/claims/M4`, its embedded
dossier, both `get_forecast` branches, and the proposal envelope. All
seven conform.

That check earned its place immediately. `envelopeSchema` was stamping
2020-12, but a Zod-rendered schema already declares draft-07 and the
spread let that label survive onto an envelope carrying 2020-12
definitions from `v0.json`. Ajv refused to compile it, which is the good
outcome; a laxer validator would have accepted a document that
misdescribed its own dialect. The dialect is now decided deliberately,
and a test pins that any schema carrying `$defs` declares 2020-12.

An existing guard also did its job unprompted: `canonical-urls.test.ts`
caught a hardcoded origin in a new doc comment. The comment was reworded
rather than the guard weakened.

## Decisions worth remembering

- **A rubric changes whether a number is worth chasing.** Session 42 was
  right to stop while the scoring was opaque and right to say so. The
  moment the release log disclosed the weights, every remaining point
  turned out to be a genuine improvement to the tool surface. The
  reversal is the evidence changing, not the judgement.
- **Absence in a rubric is evidence too.** Config schema, prompts and
  resources score nothing, which retroactively confirms three refusals
  made on other grounds and explains a null result nobody could account
  for at the time.
- **Derive the hints from the handler, not the tool.** Annotations and
  input schemas now come from the same discriminant the executor uses, so
  a tool cannot advertise behaviour it does not have.
- **A binding schema has to be checked against real output.** The spec's
  MUST is the whole risk in declaring `outputSchema`. Validating live
  documents took minutes and caught a dialect mismatch that reads as
  correct in a diff.
- **`merged: false` as a literal, not a boolean.** The schema should
  describe the states the server can actually produce. A boolean here
  would invite a client to handle a case that cannot occur.
