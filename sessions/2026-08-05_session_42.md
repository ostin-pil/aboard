### 2. The collision was real, and dissolved rather than resolved

Session 40's lead was accurate. Smithery documents a static card at
`/.well-known/mcp/server-card.json` carrying
`serverInfo`/`authentication`/`tools`/`resources`/`prompts`, and says
serving it will "bypass scanning entirely".

Three facts turned "two schemas want one path" into a non-problem:

- **The shapes have no overlapping top-level keys.** Registry uses
  `name`/`title`/`description`/`version`/`websiteUrl`/`repository`/`remotes`;
  Smithery uses `serverInfo`/`authentication`/`tools`/`resources`/`prompts`.
  Name and version appear in both specs, at different positions.
- **The registry schema permits extra keys.** `server.schema.json`
  (2025-12-11) sets no `additionalProperties: false` on `ServerDetail`, so
  a superset document is a valid registry card.
- **The registry is push-based, and only one path feeds it.**
  `scripts/publish-registry.sh` hard-codes
  `public/.well-known/mcp.json`: it runs `mcp-publisher validate` on that
  file, refuses to publish unless it matches production byte for byte, and
  uploads it. Nothing fetches either URL.

That third point is the whole answer. The two paths were interchangeable
when session 30 created them, which is why making them identical was a
sound hedge against the four spellings then in circulation. Session 33's
publish script is what stopped them being interchangeable, and no session
had noticed that the hedge had become an asymmetry.

### 3. The release was published, and falsified the premise

The operator published a Smithery release. The rescan ran and picked the

    tools: 9    resources: [claim-graph]    prompts: []    security: null

The release-log warnings and the quality score are therefore independent.
The score is also not reachable: the `score` field the search API returns

### 4. The card was declined, on Smithery's own framing

The static card exists for servers whose scan *cannot complete* — an auth
wall, bot protection, required configuration. Ours completes and reports
accurately. Adopting the shape would have replaced working live-scanned
metadata with hand-maintained assertions needing a generator and a gate to
stay honest, in order to move a number that demonstrably did not respond
to the one dimension that was fixed. It would also have dropped `remotes`,
which is the only field in the card that tells a generic agent where to
connect; Smithery's shape carries no endpoint URL because Smithery already
holds one from the listing.

Pinned in `worker/README.md` so the next session that meets the warning
does not re-litigate it, in the same place session 40 pinned the
`prompts` reasoning.

### 5. The defect the investigation actually found

`public/.well-known/mcp.json` and `public/.well-known/mcp/server-card.json`
are byte-identical, hand-maintained, and nothing was watching them. No
test, no check script, no generator. Editing one and not the other leaves
the SEP-era path serving a stale card.

It is the same drift session 33 deleted the root `server.json` to avoid,
reintroduced at a different pair of paths and never noticed, because
session 30 created both files in one commit so they had never had the
chance to diverge.

The version compounded it: `0.1.0` has four hand-written homes
(`package.json`, `SERVER_VERSION` in `protocol.ts`, and both cards), and
`SERVER_VERSION`'s doc comment already claimed to mirror `package.json`
with nothing checking the claim.

`src/lib/mcp/server-card.test.ts` pins all of it in six assertions: the
mirror, version against `SERVER_VERSION`, version against `package.json`,
the remote against the canonical `/mcp`, `websiteUrl` on the canonical
origin, and the name inside the DNS-verified `me.untype/*` namespace.

It rides `npm test`, which the manifest already gates on, so no
`build_commands` or manifest change was needed.

The assertions were mutation-tested rather than trusted: drifting the
mirror, bumping the version, and repointing the remote each failed on
exactly the expected test and nothing else, and the tree was restored
clean afterwards. A guard that has never been observed failing is a guard
nobody has checked.

### 6. Verification looks like a better lever than the score

We are `verified: false`. Verification is reachable by independents:
`exa`, `onesignal/onesignal`, `theagenttimes/news` and
`support-9ef4/Wayforth` are all `bySmithery: false, verified: true`, and
that last one's auto-generated namespace shows it is not brand-gated.
Smithery's docs put it at Settings, Verification as an "automatic
official-vendor verification checklist"; we already control `untype.me`
DNS from the registry work.

The interesting part is where verified servers sit. Sampling 150 servers
in default order gave 17 verified in the first 50 and zero in the next
100, and `useCount` does not explain the ordering (page 1 bottoms out at
7,005 while page 2 tops out at 131,031). For a listing with 0 tool calls
in 30 days, ranking is worth more than 78 against 85.

Held loosely: pages 2 and 3 returned the same maximum `useCount`, so the
pagination may be unstable and this is one sample, not a proven rule.

## Decisions worth remembering

- **A hedge can quietly become an asymmetry.** Two identical files at two
  paths was correct in session 30 and still looked correct in session 42,
  because the thing that changed was a script written three sessions later
  that named one of them. Reading the consumer, not the artifact, is what
  settled which path was free.
- **The card was declined for the same reason session 40 declined the
  config schema.** Both were cosmetic fixes to a scanner warning that
  would have cost something real: the schema a security decision, the card
  a working live scan traded for hand-maintained assertions. The scanner
  warning is a claim about the scanner too.
- **A number nobody publishes the rubric for is not a target.** The
  release cleared the warning it was supposed to clear and moved the score
  by zero. That is enough to stop optimising it and go looking for a lever
  that is visible in the data, which is what verification turned out to be.
- **Mutation-test a guard before believing it.** Six assertions passing on
  a correct tree says nothing about whether they can fail. Three
  deliberate breakages, each landing on the expected test, is what makes
  the guard evidence.
- **The stale-briefing failure reproduced against the session that
  documented it.** Session 41 wrote the finding; session 42 hit it within
  a day. It is a tooling gap, not a lapse in care, and it will keep
  recurring until session-start re-fetches before acting.
