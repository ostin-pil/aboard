## What happened

### 1. What is actually at stake

Two tracked shell scripts, both consequential:

| Script | What it does |
| --- | --- |
| `bin/check-prose.sh` | the prose gate itself (`prose_gate` in the manifest) |
| `scripts/publish-registry.sh` | derives a signing key, then writes to the public MCP registry |

Neither is a convenience wrapper. A silent break in the first turns the prose
gate into a no-op that reports success, and the second reads a P-384 private key
and publishes a card the world resolves.

### 2. The question is not "should shell count as code"

It obviously should. The real question is what widening `code_globs` would
actually cause to run, and the answer is: four commands that cannot see a shell
script. `build_commands` is `npx tsc --noEmit`, `npm run lint:resolution --
--strict`, `npm run build`. `test_commands` is `npm test`. `tsconfig.json`
includes `**/*.ts`, `**/*.tsx`, `**/*.mts`. `vitest.config.ts` includes
`src/**/*.test.ts`. No `.sh` anywhere.

That was tested rather than reasoned about. `bin/check-prose.sh` was replaced
with three lines that bash refuses to parse (`bash -n` exits 2, shellcheck
reports SC1073 and SC1072), and the whole gate was run against that tree:

| Command | Result against a shell script that does not parse |
| --- | --- |
| `npx tsc --noEmit` | exit 0 |
| `npm run lint:resolution -- --strict` | exit 0, 0 findings |
| `npm run build` | exit 0, full static export |
| `npm test` | exit 0, 331 passed |

So adding `"*.sh"` to `code_globs` on its own would have converted session 43
from a session that ran nothing into a session that ran two minutes of
ceremony and still learned nothing about the file it changed. Worse than the
status quo, because a green gate reads as verification.

### 3. Widen it, but only in company

The decision is to add `"*.sh"` to `code_globs` and, in the same edit, put
`shellcheck $(git ls-files '*.sh')` at the front of `build_commands`. The two
are one change and neither is worth making alone:

- shellcheck without the glob would never fire on the case that prompted the
  question, since a shell-only session still classifies as docs and skips the
  whole gate.
- the glob without shellcheck is the ceremony demonstrated above.

`shellcheck` runs first because it takes under a second and needs no
`node_modules`, so a shell fault fails before the type-checker starts.
`git ls-files '*.sh'` rather than `bin/*.sh scripts/*.sh` so the command tracks
whatever is in the repo, and matches the `"*.sh"` glob exactly instead of
approximating it.

The command fails closed if shellcheck is missing, deliberately unlike
`bin/check-prose.sh`. That script exits 0 on a missing tool because its caller
loops on non-zero until the prose is clean, so failing closed would spin
forever. A build gate has no such loop; a missing tool there should stop the
session.

### 4. CI too, because the manifest gate is conditional

`build_commands` only runs when a session ends, on a machine that has
shellcheck. CI runs on every pull request regardless, so the same command is now
the first step of `.github/workflows/ci.yml`, ahead of the npm install it does
not need. The two are redundant on purpose, exactly as `tsc`, `npm test` and
`npm run build` already are.

This does not contradict `.claude/rules/prose-style.md`, which keeps the prose
gate out of CI. That exemption is argued on prose being a style gate on
human-facing text rather than a correctness gate on the product. shellcheck is
the second kind.

### 5. One existing finding, annotated rather than silenced

At default severity shellcheck was not clean: SC2016 on
`scripts/publish-registry.sh` line 54, where a `node -e` program is single
quoted so its `${...}` reaches node unexpanded. That is correct code and a true
false positive, so it took a `# shellcheck disable=SC2016` at the site with a
comment saying why, rather than a repo-wide `--severity=warning` floor. Starting
strict and relaxing on evidence is the better order; the floor is one flag away
if info-level noise ever becomes a problem.

Session 43's log recorded "`shellcheck bin/check-prose.sh` clean", which was
true of that one file. The other script was never scanned.

## Decisions worth remembering

- **A classification is only worth as much as the commands behind it.**
  `code_globs` does not verify anything; it decides whether other commands run.
  Widening it without checking what those commands read produces a green gate
  over an unexamined change, which is worse than an honestly skipped one.
- **Test the gate against a broken input, not a working one.** Every command in
  `build_commands` passed on a shell script that bash cannot parse. Reading the
  configs would have suggested that; running it settled it in one minute.
- **Fail closed in a build gate, fail open in a lint loop.** The prose gate's
  exit-0-on-missing-tool is right for a caller that retries until clean and
  wrong for a caller that runs a command once and reports. Same repo, opposite
  answers, and the difference is the caller.
- **Annotate a false positive at the site; do not lower the floor.** One
  SC2016 on deliberately literal quoting is a two-line comment. Dropping the
  whole repo to `--severity=warning` to avoid it would have discarded every
  future info-level finding to silence one.
