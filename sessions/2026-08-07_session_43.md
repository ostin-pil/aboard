## Context

The last open item from the 2026-08-05 investigation into why aboard's prose
gate kept changing under it. That entry ended undecided, because both options
were bad: pinning to a release meant downgrading, and keeping the symlink meant
the gate tracked a working tree. Publishing prose-mint 0.1.1 removed the first
objection, so this session made the change.

## What happened

### 1. What the resolver was actually doing

`bin/check-prose.sh` tried `prose-mint` on `PATH`, then
`~/Projects/prose-mint/bin/prose-mint`. Nothing on this machine puts prose-mint
on `PATH`, so the second branch was never a fallback; it was the only path that
ever ran. And `~/Projects/prose-mint` is a symlink to
`~/Projects/claude-plugins/prose-mint`, whose `bin/prose-mint` is a launcher
that runs the package from the checkout with no install.

So the gate ran whatever branch claude-plugins had checked out, uncommitted
edits included, and said nothing about it in the output. On 2026-08-05 that
meant a feature branch.

### 2. Why it was safe to change now, and was not before

The 2026-08-05 entry deferred on the grounds that the newest published
prose-mint was 0.1.0 while the checkout was ahead of it, so pinning would move
the gate backwards. That was true then. 0.1.1 had been tagged since 2026-07-12
and never published: the release workflow failed on a PyPI Trusted Publisher
exchange and was never retried. Re-running it published, and the published
0.1.1 package is byte-identical to the checkout, so the switch costs nothing in
behaviour today.

### 3. The change

`uvx prose-mint` replaces the checkout path. `PROSE_MINT_VERSION` pins an exact
release and is empty by default, tracking the latest, which is what the
prose-mint plugin's own `prose-check` skill and command already do. Matching
them was the tiebreaker: a project consuming this tool two ways should not
resolve it two ways.

`TOOL` became an array, because `uvx prose-mint` is a command plus an argument
rather than a path, and the two `exec` sites expand it as `"${TOOL[@]}"`. Bash
here is 3.2, which handles a non-empty array under `set -u` fine; the array is
only ever expanded after a successful resolve.

### 4. Verified by comparison, not by inspection

The point of the change is that behaviour should be identical while the source
of the code changes, so the test is a before-and-after on the same input.
`sessions/2026-08-05_session_41.md` had been scanned earlier through the
symlink and reported one em-dash hit. Through `uvx` it reports one em-dash hit,
on the same line.

Three other paths checked, since the resolver is the only thing that moved:

| Path | Result |
| --- | --- |
| `--file` scan | identical hit count on a known file |
| `--stdin --strict` with a planted em dash | flags it, exits 1 |
| `--stdin` clean input | exits 0 |
| neither `prose-mint` nor `uvx` on `PATH` | warns on stderr, exits 0 |

That last one matters more than it looks. The gate fails open on purpose: the
caller reads a non-zero exit as "findings to rewrite" and rescans until clean,
so failing closed on a missing tool would spin forever.

## Decisions worth remembering

- **A fallback that is the only reachable branch is not a fallback.** The
  resolver read as "prefer an install, fall back to a checkout", and on this
  machine the first condition never held, so the documented preference had
  never once applied. Worth checking which branch of a resolver actually runs
  before trusting the order it is written in.
- **Test a source-of-code change by comparing outputs, not by reading the
  diff.** The change is only correct if behaviour is unchanged, and the one
  cheap way to know that is to re-run something already run through the old
  path.
- **Resolve a tool the same way everywhere.** The prose-mint plugin's skill and
  command already resolved through `uvx`; only this script did something else,
  and the something else is what drifted.
- **`PROSE_MINT_VERSION` is empty on purpose.** Tracking the latest release
  matches the plugin and keeps one moving part instead of two. An exact pin is
  one assignment away if a release ever changes the gate's verdicts unexpectedly.
