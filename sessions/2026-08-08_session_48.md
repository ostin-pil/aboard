### 2. The root tsconfig only half-covered its own glob

`tsconfig.json` excludes `clients` and `mcp-server`. So `"*.ts"` in
`code_globs` classified a change to either package as a code session, and then
`npx tsc --noEmit` did not read the file that changed. Planting a type error in
`mcp-server/src/types.ts` and another in `clients/schema-loader.ts` and running
the whole gate settled it:

| `npm run lint` | exit 0 |

| `npm run build` | exit 0 |
| `npm test` | exit 0, 341 passed |

Six for six. This is the same shape as sessions 45 and 46, one directory over,
and it is the more dangerous version: the glob was already present, so the
classification looked correct while verifying nothing.

### 3. `clients/tsconfig.json` had never been executed by anything

Installing the sub-package dependencies to separate real errors from
missing-module noise turned up two errors in `clients/` that were nobody's
doing this session: `TS5097` on `briefing.ts:18` and `validate.ts:16`, both
importing `./schema-loader.ts` with an explicit extension while
`allowImportingTsExtensions` was off.

The config had been failing since it was written. Three things had to be true
at once for that to go unnoticed, and they were: the root tsconfig excludes the
directory, CI ran only `npm ci` there, and `tsx` strips types without checking
them. A tsconfig with no command behind it is the same hollow artifact as a
glob with no command behind it, and it had been sitting in the repo longer.

`allowImportingTsExtensions` is the right fix rather than rewriting the
imports: `noEmit` is set, so nothing rewrites those paths, and what `tsc` reads
is exactly what `tsx` runs.

### 4. The Worker dry-run is narrower than its name

This one was expected to be an easy addition and turned out not to be worth
adding. Three probes, all against a tree where `npx tsc --noEmit` exits 0:

| Planted break | `wrangler deploy --dry-run` |
| --- | --- |
| unknown `compatibility_flag` in `wrangler.jsonc` | exit 0, silent |
| `import { readFileSync } from "node:fs"`, no `nodejs_compat` | exit 0, warning only |
| `main` pointing at a renamed entry file | **exit 1**, names the file |

So it does not validate the config and does not enforce the Workers runtime
surface. What it checks is the wiring between `wrangler.jsonc` and the code.
Worker *types* are already covered, because the root tsconfig does include
`worker/` (three files, confirmed with `--listFilesOnly`). One narrow seam did
not justify a wrangler download on every session end, so it stays in CI with
the measurements written at the step.

### 5. `check:built-urls` is partly redundant, and the remainder matters

The first probe for this one, deleting `metadataBase` from `layout.tsx`, turned
`npm test` red. `src/lib/canonical-urls.test.ts` greps the source for that
exact line. So the gate was not blind to the regression the checker was
originally written for.

That test greps source, though, and `check:built-urls` asserts over built HTML.
Re-probing with a hardcoded `http://localhost:3000` link in the layout
separated them: `tsc`, `npm test`, `npm run lint` and `npm run build` all exit
0, and `check:built-urls` exits 1 with 172 forbidden URLs across 137 files.
Non-redundant, cheap, no new dependency, so it went in, ordered after the build
whose output it reads.

### 6. Nothing validates the JSON-LD against its own schema in-process

`edgeLD` in `src/lib/jsonld.ts` has no declared return type. Dropping
`aboard:rationale` from it therefore type-checks: inference just produces a
narrower object type, and no downstream signature pins the shape. That break
passed all six gate commands and was caught only by the served-export
validation in CI, which named the missing property on every edge.

`public/schema/v0.json` is described in `CLAUDE.md` as the authoritative spec,
and the rule is that `jsonld.ts` and the schema change in the same commit. The
check that would enforce it exists in exactly one place, needs a running static
server, and `ajv` is a dependency of `clients/` rather than of the root
package. Closing it properly means an in-process test and a root dependency,
which is a session of its own rather than a line in an audit. It is recorded as
a known hole in `CLAUDE.md` and in "What's next" below.

### 7. Self-provisioning rather than a guard

The two new sub-package commands are root scripts:

```
"typecheck:mcp": "cd mcp-server && (test -d node_modules || npm ci) && npm run typecheck"
```

The manifest has a `subpkg_guard` key designed for exactly this, which runs the
final `test_commands` entry only when a path exists. It was left as `none` on
purpose. `mcp-server` is committed and never absent; only its `node_modules`
can be, so a guard on that path would skip the check on precisely the machine
that had never installed it. That is a fail-open, and this session exists to
remove fail-opens. Provisioning inside the command fails closed instead, and
costs one install per clone.

Verified cold, with `clients/node_modules` moved aside: exit 0, directory
recreated. Verified in the failing direction: exit 2 from both.

### 8. What was deliberately not added

`"*.jsonc"` is not in `code_globs`. `wrangler.jsonc` is deployment-critical and
no gate command reads it, so adding the glob would be the hollow-glob mistake
the comment above `code_globs` exists to prevent. The absence is now argued in
that comment rather than left as an oversight.

### 9. The classification skipped the gate on this very session

Auto-detection classifies this session as config/docs. Not one of the six
changed files matches `code_globs`: two `.md`, one `.yml`, three `.json`. A
session that rewrote `build_commands` itself skips phase 1.

The full gate was run by hand on this exact tree immediately before the
commits, so nothing here is unverified. But the shape is the same one sessions
43, 45 and 46 each hit from a different direction, and it is now clearly a
recurring structural gap rather than three coincidences. It wants the same
empirical treatment, and it is the first item in "What's next".

## Decisions worth remembering

- **A glob can be present and still hollow.** Sessions 45 and 46 both added a
  missing glob. This one found `"*.ts"` already there and only half-honoured,
  because the root tsconfig excludes two directories full of `.ts`. Checking
  that a glob exists is not checking that a command reads the files it matches;
  `tsc --listFilesOnly` answers the second question in one command.
- **A config file is an artifact with the same failure mode as a glob.**
  `clients/tsconfig.json` had been failing since it was written because nothing
  ever ran it. The lesson generalises past `code_globs`: any config that no
  command executes is decoration, and it will drift silently.
- **Measure the check you are about to trust, including the ones you plan to
  keep.** The wrangler dry-run was expected to be a straightforward win and
  turned out to pass two of the three breaks aimed at it. That result changed
  the decision from "add it to the gate" to "keep it in CI and write down what
  it does not do".
- **Redundancy is a reason to re-probe, not to skip.** `check:built-urls`
  looked redundant the moment `npm test` caught the `metadataBase` probe. The
  second probe, aimed at what a source-grep test cannot see, showed the overlap
  was partial and the remainder was worth having.
- **Provision inside the command rather than guarding around it.** A path guard
  would have skipped the sub-package type-checks on any machine that had not
  installed them, which is the fail-open this session set out to remove. Same
  reasoning as session 45's fail-closed build gate, applied to a missing
  `node_modules` rather than a missing tool.
