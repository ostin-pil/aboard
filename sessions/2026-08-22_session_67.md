## What happened

### 1. M4 — the package that was installable and not runnable

`mcp-server/package.json` had `bin` pointing at `src/index.ts` behind an
`#!/usr/bin/env -S npx tsx` shebang. That resolves only inside a checkout
of this repo with tsx already present, so the package npm would have
served was inert for every consumer the registry card and the README
send there. `private: true` meant nobody had found out.

`tsconfig.json` now emits. `noEmit` is gone from the file and passed on
the command line by `npm run typecheck` instead, so the configuration
being type-checked is the one that produces the artifact rather than a
second one that happens to agree with it. Module resolution moved from
`Bundler` to `NodeNext`, which is what Node performs at runtime.

The interesting part is that no source file had to change for that move.
Every relative import in `mcp-server/src/` already carried an explicit
`.js`, which `Bundler` tolerated and `NodeNext` requires. The switch
type-checked clean on the first run.

`prepack` runs the build and copies the root LICENSE into the package
directory, which `.gitignore` then keeps out of version control. That
gives the tarball the licence text Apache-2.0 requires recipients be
given without this repo holding a second copy of it. `npm pack
--dry-run` shows 8 files, 13.3 kB.

Verified the way the chunk plan asks rather than by inspection: packed a
tarball, installed it into an empty directory, ran `npx
aboard-mcp-server` against the live site. Nine tools on `tools/list`, 25
claims across three domains from `list_claims`. Repeated after the
operator published, from the registry rather than a local tarball: `npx
-y aboard-mcp-server@0.1.0` in a clean directory answers identically.

### 2. `clients/` was decided rather than published

The chunk asked for its fate to be settled instead of left
half-declared. The first draft of the argument against publishing was
that `schema-loader.ts` resolves `../public/schema/v0.json` relative to
its own file and would therefore break once installed under
`node_modules`, with the HTTP fallback documented in its own README as
pointing at a route that does not exist.

Checking that claim against the deploy killed it. `output: "export"`
copies `public/schema/v0.json` to `out/schema/v0.json`, and
`https://aboard.untype.me/schema/v0.json` answers `200
application/json`. The README note had gone stale when the app became a
static export, and nothing had reread it since. Publishing turned out to
cost about half an hour, and the package would embed no schema, so it
would not even have to version in lockstep with one still in flux.

The decision came down on fold-into-docs anyway, for a reason that
survives the correction: M4's complaint is that the distribution story
points at a package nobody can install, and that story is entirely the
MCP server's. The README, `CONTRIBUTING.md` and the registry card all
name `aboard-mcp-server`, so a reader following any of them hits a
package that has to exist. Nothing anywhere advertises `aboard-clients`,
so publishing it closes no gap a reader can walk into, while a published
name implies an API stability that "reference adapter" is meant to
disclaim.

The stale limitation was corrected in the same commit, since the
argument had been resting on it.

### 3. M3 — the card, and the fifth version home

Both cards gained a `packages` entry: npm registry, `aboard-mcp-server`,
pinned version, stdio transport, and both environment variables with the
agent token marked `isSecret`. The shape was read off the 2025-12-11
server schema rather than recalled, and `mcp-publisher validate` passes
against the live registry.

That entry made `mcp-server/package.json` a fifth hand-written home for
a version, and the first that is also a claim about a third-party
registry. The failure it invites is quiet: bump the npm package, forget
the card, and the registry directs every client at a version that is no
longer latest, with tsc, the tests and the build all green because none
of them reads npm. Five assertions in `server-card.test.ts` now relate
the card to the package it advertises, including that `bin` still points
at built output and that `private: true` has not come back. Planting a
version bump on one card fails two of them, the new pin and the existing
mirror check.

They deliberately do not call npm. A network round trip would make `npm
test` fail offline and on a rate limit, and the drift worth catching
lives between two files in this repo.

### 4. The registry re-publish, and why it needs a version bump

The card the registry serves is the 2026-07-29 one: `remotes` only, no
`packages`. So an agent discovering aboard through the official registry
never learns the npx path this session built. Fixing that means running
`scripts/publish-registry.sh` again, and the registry rejects a
duplicate version, which session 63 already recorded hitting.

The card version therefore moved to `0.1.1` in four homes: root
`package.json`, `SERVER_VERSION`, and both cards. `packages[0].version`
stayed at `0.1.0`, and `mcp-server/package.json` with it. The two axes
are independent on purpose: the card version identifies the registry
entry, and the package version identifies what npm actually serves, so
bumping the second would advertise a release that does not exist.

The lockfile carries the root version twice, which the plan document had
not predicted, so the bump is five lines rather than four. `npm install
--package-lock-only` was the wrong instrument for it: alongside the two
version lines it re-added 66 lines of bundled
`@tailwindcss/oxide-wasm32-wasi` optional dependencies that the
committed lockfile had pruned. Reverted and hand-edited, so the commit
is a version bump and nothing else. Worth knowing before the next
lockfile touch, because npm will want to do it again.

The publish itself could not run in this session and this is a property
of the script rather than a missing step. It fetches
`https://aboard.untype.me/.well-known/mcp.json` and refuses to continue
if it differs from the local card, on the argument that publishing a
card production does not serve would put a lie in the registry. The
bumped card is on this branch, so production still serves `0.1.0`. The
publish is therefore the first thing to run after this PR merges and
deploys, and `plans/distribution-listings.md` carries the ordering.

`mcp-publisher` is on PATH and the `mcp-publisher-untype` keychain entry
is present, both checked, so nothing blocks that run except the deploy.

For awesome-mcp-servers that meant reading the actual file rather than
guessing at it. The entry belongs in `🔬 Research` (`🧠 Knowledge &
Memory` is about agent memory stores), sorts between `OrgMentem/zotio`
and `ovlabs/mcp-server-originalvoices`, and carries `📇 ☁️ 🏠 🍎 🪟 🐧`
with each symbol checked against the README's own legend. `🎖️` is left
off with the reason recorded, since it qualifies on the letter of the
legend and reads as a vendor badge in practice.

For Search Console the recommendation is a domain property on
`untype.me` rather than a URL-prefix property on the subdomain. The
usual objection is that a domain property pools every subdomain into one
report; `dig` shows the apex has no A or AAAA record and nothing else on
the zone serves a site, so it reports aboard and only aboard while
covering any subdomain added later. It also avoids committing an HTML
file or a meta tag that would then have to live in the repo forever.

That section carries a warning rather than a step, because the apex
already holds the `v=MCPv1` TXT record that authorises registry
publishing and losing it costs a key rotation
(`knowledge/issues.md`, 2026-08-19). A name can hold many TXT records,
so the Google one is an addition; the instruction is to add a record and
to refuse any control that offers to replace the set.

## Decisions worth remembering

- **Checking the stale note is what made the argument honest.** The case
  against publishing `clients/` initially rested on a README limitation
  that had been false since the app became a static export. One `curl`
  refuted it. The decision survived on a different argument, and the
  note was fixed in the same commit, but a plan built on the first
  version would have been built on a fact nobody had reread in months.
- **A card that advertises a package has to be pinned to it.** The
  `packages` entry is the first thing in this repo that makes a claim
  about a third-party registry, and no existing command could see it
  drift. The five assertions cost less than the class of bug they
  refuse, which is a registry entry quietly pointing at a stale release.
- **The publish script's refusal is the feature.** Comparing the local
  card against production before contacting the registry is what makes
  the publish un-runnable mid-session, and that is correct: the
  alternative is a registry entry describing a card nobody serves.
  Ordering constraints that come from a safety check are worth writing
  down rather than working around.
- **`npm install --package-lock-only` is not a version-bump tool here.**
  It brought 66 lines of unrelated churn with two lines of signal. Hand
  editing the version lines is the smaller, reviewable change.
- **The operator half deserved a document, not a to-do list.** Every
  submission is a claim about aboard made to a third party, and four
  listings written independently drift. Canonical copy in one place with
  the reasoning attached is what keeps them saying the same thing.
