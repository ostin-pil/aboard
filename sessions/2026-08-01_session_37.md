## Context

Two small pieces left over from session 35, both agreed before the session
opened. The provenance label on MCP-filed proposals named the wrong door,
and the `?auth=required` endpoint that session shipped was documented
nowhere an agent would find it. Neither is large; the second turned out to
have a better answer than the one planned.

## What happened

### 1. A proposal now names the door it came through

Every claim filed through `/mcp` carried `promptTitle: "Agent proposal via
/api/proposals"`. Both routes share `runProposal`, so the label was true
about the pipeline and wrong about the entry point, and nothing else in the
record distinguished an MCP filing from an HTTP one. It is visible on
`ECM2`, the first claim an outside agent filed.

The three builders that stamp attribution (claim, prediction, dossier;
edges carry none) now take a `via` label, and each transport names itself:
`POST /api/proposals` from the HTTP endpoint, `MCP propose_claim` and its
siblings from the tool shell.

The label travels beside the envelope rather than inside it. The envelope is
Zod-validated and would drop an unknown key, but the real reason is that
provenance a caller can assert is worthless: this is the rule that already
keeps `operator` server-side, and `via` is subject to it. Three tests cover
the behaviour, including one that feeds a payload trying to declare its own
`via` and asserts the attribution ignores it.

### 2. Documenting `?auth=required`, and where that turned out to belong

The plan was to document the authenticated URL on the agent-facing surfaces
and to append a note to the Smithery listing description. The first half was
straightforward: `/auth.md` gained a section explaining the gateway failure
mode and the fix, `/llms.txt` a pointer, and `/about` a sentence. All three
were checked in the built output rather than in source.

The Smithery half did not survive contact. Its settings page offers Display
Name, Description, Homepage, GitHub Repository, an icon and an Unlisted
flag, and no README or long-description field. The Description is therefore
the only prose surface, and it is the text the semantic search indexes,
which is exactly what session 33 fixed to make the listing findable at all.
Spending that on OAuth instructions is a bad trade, so the listing was left
untouched.

The better home was found by checking what actually survives a gateway. A
gateway that aggregates several servers answers `initialize` with its own
`serverInfo` and drops ours, so `SERVER_INSTRUCTIONS` never reaches those
callers. Tool descriptions pass through verbatim, which was confirmed by
reading `propose_claim`'s description back through Smithery's namespace
endpoint. So the note went there: the four write tools now share one
`WRITE_AUTH_NOTE` constant instead of four drifting copies of the same
closing sentence.

That reaches every gateway user of every gateway rather than one listing's
readers, and it costs the search ranking nothing.

## Decisions worth remembering

- **Provenance fields travel outside the validated envelope.** `via` joins
  `operator` and `agentId` in the set of things stamped by the shell that
  saw the request, never read from what the caller sent.
- **Check what survives the intermediary before choosing where to write.**
  `SERVER_INSTRUCTIONS` looked like the obvious home for connection-level
  guidance and is dropped by aggregating gateways; tool descriptions are
  passed through verbatim. One `tools/list` call through Smithery settled
  it.
- **A listing's description is its search index.** On Smithery there is no
  second prose field, so anything added there competes with
  discoverability. Session 33 paid to learn that an empty description makes
  a listing invisible; the same fact says not to dilute a good one.
- **`ECM2` keeps its old label.** Attribution records what the system
  stamped at the time. Editing committed provenance to look retroactively
  correct is a worse precedent than one imprecise label on one claim.
