## What happened

### 1. The follow-up as written was wrong on both halves

`resources/list` and `prompts/list` answering `-32601` is not a gap. The
lifecycle spec is explicit that during operation both parties **MUST**
"only use capabilities that were successfully negotiated", and aboard's
`initialize` declares `capabilities: { tools: {} }` and nothing else. A
client that calls `resources/list` against that declaration is in
violation, and `-32601` is the correct answer. Smithery's scanner calls
both anyway and logs the errors as defects.

Production was probed before any code was written, and matched the
source exactly: `-32601` for both, `{"tools":{}}` from `initialize`. So
there was nothing to reproduce and nothing broken.

The config-schema half is worse than unnecessary. Session 33 recorded
that the Smithery listing was published 2026-07-26 with an empty
`configSchema`, and that this is what makes session 30's decision hold
that no token may transit the gateway. The only configuration this
server could plausibly accept is a credential. Supplying a config schema
would reverse a standing security decision in order to quiet a cosmetic
warning, so it was not done and the schema stays empty.

### 2. What was built instead

Tools are model-driven actions; resources are application-driven context
a host can list, pick and read without the model asking. `get_graph` and
`get_claim` are documents wearing a tool costume, so the same documents
are now addressable as resources. This makes the `resources` declaration
honest, which is the only reason to make it: silencing the scanner is a
side effect, not the goal.

`src/lib/mcp/resources.ts` is a new pure module holding the catalogue and
URI resolution. `protocol.ts` declares `resources: {}` beside `tools: {}`
and routes `resources/list`, `resources/templates/list` and
`resources/read`; the read produces a new `resource` plan kind that
`worker/mcp.ts` executes against the assets binding, which is the shape
`tools/call` already had.

Four decisions inside that, each with a live alternative:

- **`https://` URIs, not a custom `aboard://` scheme.** The spec reserves
  `https://` for resources a client could fetch itself and prefers a
  custom scheme otherwise. These genuinely are fetchable: public,
  CORS-open, served at that exact path. A custom scheme would assert an
  indirection that does not exist.
- **One concrete resource, one template.** Enumerating every claim in
  `resources/list` would make it an IO operation, since it would have to
  read the graph to learn the ids, and the protocol layer is pure by
  construction so the wire behaviour is testable without a network.
  Per-claim reads are `https://aboard.untype.me/api/claims/{id}` instead,
  with `list_claims` named in the template description as how a caller
  discovers ids — a template with no companion enumeration is a dead end.
- **`-32002` at HTTP 200, not 404.** A 404 is how the modern era says "no
  such method", so using it for a resolved method reporting a missing
  document would make the two indistinguishable. Both the unresolvable
  URI (caught in the pure layer) and the resolved URI whose document is
  absent (caught in the Worker) answer the same way.
- **Origin-strict resolution.** Only the canonical origin resolves.
  Being lenient would let `https://anywhere.example/api/graph` quietly
  read our own graph — harmless, since only the path is ever used, but it
  would say something untrue about what was read.

`prompts` stays undeclared and unimplemented. Declaring an empty
capability buys nothing but a wasted round-trip per connection, and it
would be a promise to serve something we do not. That reasoning is
pinned in a test and in `worker/README.md` so a later session does not
undo it by reflex when the warning reappears.

That probe is also what caught the one error made this session. A doc
comment claimed the resource URI and the JSON-LD `@id` were the same
string. They are not: a claim's `@id` is its page (`/claims/M4`) and its
JSON-LD is served at `/api/claims/M4`. The comment was rewritten to say
what is true, which is that the resource URI names the document a client
gets back and could re-fetch.

scan runs at all. Not chased: it is a separate question from this slice

## Decisions worth remembering

- **A scanner's warning is a claim about the scanner too.** Both
  release-scan warnings were reporting Smithery calling methods the spec
  forbids it from calling against our declaration. Reading the spec
  before implementing turned a 30-line appeasement into a real feature
  and stopped a security decision from being reversed by accident.
- **Declaring a capability is a promise to serve it.** The empty-capability
  shortcut is available for `prompts` and was refused: it costs a
  round-trip per connection on every client and states something false.
  When the warning returns, that is the answer.
- **`-32002` at HTTP 200, because 404 already means something here.** The
  modern era uses 404 for "no such method"; reusing it for "no such
  document" would collapse two distinct answers into one status.
- **Purity is what kept `resources/list` cheap.** Listing every claim
  would have dragged IO into the layer that is pure so it can be tested
  without a network. The template is not a compromise, it is the
  mechanism the spec provides for exactly this.
- **A live probe is worth more than a careful reading of one's own
  comments.** The `@id` error was in prose that looked obviously true and
  was disproved in one request.
