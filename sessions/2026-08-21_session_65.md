### 2. E16 — every directory listing sorts

`readDirIfExists` in `loader.ts` now sorts, which covers claims,
forecasts, dossiers and analyses in one place. `listDomains()` had
sorted since it was written and the three per-domain listings never
had, so `/api/graph` arrays reordered between filesystems for no change
in `data/`.

The test is the interesting half. `vitest.config.ts` had argued the
unit project stays out of the loader because the build covers that path
end to end, and that argument holds for everything the loader *parses*
— the build runs the same schemas over the same files. It does not hold
for ordering, because the build reads `data/` once, on one filesystem,
and validates whatever order it gets. So `loader.test.ts` mocks
`server-only` away and reverses `readdirSync`, then asserts sorted
order; the config comment was revised with that exception and its
reason. Reversal rather than a shuffle, so a failure is the same every
run. Planting the fault (removing `.sort()`) fails four assertions.

### 3. E15 — the one-liners

`appendEdgeToYaml`'s empty-file guard was `trimmed === "[]"`, true of
exactly one spelling of an empty file. `[] # reserved for cross-domain
edges` — the shape an author reaching for that file is most likely to
leave — took the append branch and produced a flow sequence followed by
a block sequence, which is not YAML. The guard now parses, and any
comment the empty file carried is preserved above the first edge.
Restoring the old guard fails the two new cases with a YAML parse
error, which is the fault reproduced rather than asserted.

`nextSequentialId` interpolated its stem into a `RegExp`. It now
matches by string operations, so a stem is text rather than a pattern.
The remaining two items were decisions to write down rather than code
to change: `/api/proposals` has no OPTIONS branch because the only
caller a preflight could serve is a browser page holding a write
credential, and the claims route's 404-JSON branch is unreachable under
`output: "export"` but live in `npm run dev`, which is a dev/prod
contract fork worth naming at the site.

### 4. E12 — edge identity, and the plumbing the plan did not name

The chunk plan said the exporter's graph already carries canonical ids
for seeded edges. It does not: `EngineEdge` had no id field, so the ids
stop at `engine-adapter.ts` and never reach the exporter. `canonicalId`
and `strength` now ride through the adapter, `engineToRF` and
`rfToEngine`, with absence as the signal that an edge was drawn in the
sandbox and needs an id minted.

Two remedies were on the record and they disagreed: the chunk plan said
emit `edges.yaml` as the merged set, the E12 row said emit
append-fragments. The merged set won, because a fragment cannot express
a deletion or a retarget and the sandbox is an editor over the real
graph. That decision is what forced `strength` to be carried as well —
emitting the merged set without it would have written every
reviewer-tuned number back at the `0.5` placeholder, turning a loud
defect into a quiet one.

`nextSequentialId` and `inferDomainPrefix` moved to a new `src/lib/ids.ts`
that imports nothing at runtime. The exporter runs in the browser and
`proposals.ts` pulls in Zod, so reusing the real minting rule from
there would have undone session 61's bundle diet (P2). The sandbox and
the API now mint under one implementation rather than two copies of a
convention.

`exporter.test.ts` is new: synthetic fixtures pin the id and fidelity
rules edge by edge, and a final block runs the real graph through
`data/` to loader to `toEngineData` to `engineToPRPack` and asserts the
pack is a no-op against the files it claims to replace. Ignoring
`canonicalId` fails eight of its assertions.

### 5. The defect the exporter suite found

A sandbox-drawn edge was emitted with `rationale` commented out, but
`Edge.rationale` is required — the schema's own comment says why, since
the graph classifies relations on stated reasoning rather than edge
counts. So the pack that this module's header promises will validate
did not, and the contributor found out at `npm run build` after
dropping it into `data/`. Drawn edges now carry
`EDGE_RATIONALE_PLACEHOLDER`, which validates and is unmissable in a
diff. Found by writing the test, not by the audit.

### 6. Stale edge ids and duplicate relations, refused at submit

Session 51 closed the deploy-lag collision window for claims and
dossiers, where it surfaces as a GitHub 422 on a create. An edge
appends to a file that already exists, so it never reached that path
and the duplicate id rode into the PR to fail CI's integrity check on
the reviewer's time.

The edge path already reads its target file at the base ref before
committing, which makes the collision knowable before GitHub is asked
to do anything. `edgeIndex` reads that file into the two things the
write path needs — every id, and every relation keyed on
`(fromId, kind, toId)` — and both checks run before a branch is cut, so
a refusal leaves nothing behind to clean up. A stale id is the same
`409 id_collision` the other two kinds return, with the same
remediation vocabulary.

The duplicate relation is refused twice on purpose: `buildEdge` asks
the deployed graph, which is free and answers before GitHub is touched
at all, and the Worker re-asks the base-ref file, which is
authoritative. It is `409 duplicate_relation` with `retryable: false`,
because filing again under a fresh id would produce a second edge
asserting the same thing, which no integrity check rejects and every
consumer then double-counts. Direction is part of the key, so the
reverse edge is allowed: it is a contradiction a reviewer should see,
not a duplicate the API should swallow.

The refusal also runs before minting, so a retried duplicate does not
burn an id and leave a hole in the sequence.

### 7. E17 — validating before `--update` writes

`ensemble-predict --update` pushed onto `predictions` and re-stringified
the whole file. Nothing validated, so a model-invented URL or an
out-of-range probability landed in `data/` and first failed at a later
build with the provider run long gone; and the re-stringify unfolded
every long string, so a one-prediction append arrived as a diff
touching every line.

Both schemas now run before the write — each prediction on its own so
the message names the provider, then the whole file — and the append
goes through `appendPredictionToForecast`, the diff-preserving writer
the Worker already uses. The parsed value is deliberately not what gets
written: `baseRates` and `dataAnchors` carry `.default([])`, so writing
it would add two empty keys to every prediction that no hand-authored
one in `data/` has.

Verified by hand against F7, because `vitest.config.ts` includes
`src/`, `worker/` and `mcp-server/` only and this script is in none of
them: 7 lines added, all 56 prior lines byte-identical, and a 1.7
probability refused naming the field.

## Decisions worth remembering

- **The merged set beat append-fragments, and that choice had a
  consequence.** Two plan documents proposed different remedies for
  E12. Only the merged set can express a deletion or a retarget, which
  the sandbox permits — and choosing it is what made carrying
  `strength` mandatory rather than optional. A fidelity decision
  followed from an expressiveness one; taking the merged set without
  noticing that would have shipped a worse defect than the one being
  fixed.
- **A shared rule is worth a module that imports nothing.** The
  alternative to `src/lib/ids.ts` was a second copy of the id
  convention inside the exporter, which is the exact shape of defect
  this repo keeps finding (`SUPPORTED_EDGE_KINDS`, the four version
  homes). The browser-bundle constraint made the honest fix a new
  module rather than an import.
- **A check that can run before the side effect should.** The edge
  collision was reachable as a pre-commit read all along, because the
  path already fetches the file it will append to. Answering it there
  rather than classifying a GitHub failure afterwards means no branch
  is cut and nothing needs cleanup, and it cost one function.
- **Writing the test is what found the rationale defect.** The audit
  had catalogued the exporter's id problem for six sessions and never
  named the required-field one. Parsing the emitted files back through
  the canonical schemas surfaced it on the first run.
- **A dropped rescue is cheaper than a duplicated one.** Two sessions
  independently landing the same two commits would have collided at
  merge. Surfacing the parallel session and asking cost one question;
  discovering it at PR time would have cost a conflict resolution on
  24 files.
