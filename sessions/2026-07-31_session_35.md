## Context

Session 33 left one question open and newly answerable: can a `propose_*`
call arrive authenticated when it comes through Smithery rather than
straight at our endpoint. Session 30 had predicted no, on the grounds that
a static bearer token cannot transit a third-party gateway. Session 31 then
shipped OAuth 2.1 with PKCE, which is the auth model Smithery speaks, so the
prediction was worth retesting rather than inheriting. The answer turned out
to be no for a completely different reason, and fixing that reason took the
session from a test into a small feature.

## What happened

### 1. The first answer was no, and the stated reason was wrong

Creating a Smithery connection against `https://aboard.untype.me/mcp`
returned `connected` immediately rather than `auth_required`. A read tool
called through the gateway worked end to end. A write returned JSON-RPC
`-32001 Authorization required` carrying an `authorizationUrl`, and
approving that setup URL changed nothing: the write kept failing the same
way, and a second approval changed nothing again.

The `-32001` was read mid-session as proof that Smithery brokers OAuth
against our authorization server. That reading was wrong, and the operator
was sent to approve a grant on the strength of it. It is Smithery's generic
"the upstream said 401" error, and no brokering had happened at all.

### 2. What the server's own logs showed

`wrangler tail` against the deployed Worker settled it, and the evidence
was unambiguous once looked at rather than inferred.

- Creating a connection produced exactly three requests:
  `GET /.well-known/oauth-protected-resource/mcp` (200), `POST /mcp`
  carrying `initialize` (200), and the follow-up notification (202).
  Discovery ran and had everything it needed.
- The failing write arrived as `POST /mcp` with **no `Authorization`
  header at all**, and got our 401. Smithery was calling us with no
  credential, not with a rejected one.
- `OAUTH_KV` held eight registered clients, every one of them session 31's
  own `127.0.0.1` test clients, and a single grant created 2026-07-28.
  Nothing from Smithery, and no token.

Both RFC 9728 metadata paths serve correct, identical documents, so nothing
on our side was missing. Smithery's own documentation closes it: the OAuth
requirement is determined by the server's initial handshake, and there is no
field to declare or force it.

The mechanism, stated once: **Smithery decides a connection's
authentication when the connection is created, and never revisits it.** Our
endpoint serves reads publicly and challenges only on writes, so the
handshake succeeds, the connection is recorded as needing nothing, and no
authorization flow ever runs. The 401 a write raises later arrives after the
only moment that client would have acted on it. Approving the setup URL
authenticates the operator to Smithery and cannot help.

Session 30's prediction was right in outcome and wrong in mechanism. The
obstacle was never that a gateway cannot hold a credential.

### 3. `?auth=required`

The fix is ours to make and it is small: challenge an uncredentialed caller
at the handshake instead of at the first write, when the client asks for it.
`handleMcp` takes an `authRequired` dep, set from a query parameter, and
raises the existing `authorizeWrite` challenge before the body is read.

A query parameter rather than a second path, deliberately. RFC 9728 derives
the metadata document from the path, so `/.well-known/oauth-protected-resource/mcp`
still describes the endpoint and a token keeps one audience. A second path
would fork both. The gate sits after the OPTIONS branch so preflight and
CORS are untouched, and the plain URL is unchanged, so no ordinary client
regresses.

### 4. It works, and the flow is visible end to end

A connection against `https://aboard.untype.me/mcp?auth=required` returned
`auth_required` with a setup URL. Completing it produced, in our logs, the
whole dance we had never seen: protected-resource discovery, authorization
server metadata, `/oauth/authorize`, `/oauth/consent`, `/oauth/callback`,
`/oauth/token`. `OAUTH_KV` gained a second grant and its first token.

Two details worth keeping.

- **Smithery authenticated by CIMD, not DCR.** Its `client_id` is
  `https://smithery.run/.well-known/oauth-client`, a URL that is its own
  metadata document, so the client table stayed at eight entries while a
  grant and token appeared. The first real third-party client to arrive
  never touched the registration endpoint.
- **The audience survived the query string by existing design.** The
  authorize request asked for `resource=https://aboard.untype.me/mcp?auth=required`,
  and `normalizeResource` in `src/lib/mcp/auth.ts` builds from protocol,
  host, port and pathname, so the query is dropped and the audience
  resolves to `RESOURCE_URI` unchanged. The query-parameter design was
  compatible with audience validation without touching it.

An empty-argument `propose_claim` was used as the probe, because auth is
checked before validation: it came back `HTTP 422 invalid_envelope`
complaining that a rationale is required, which proves the token reached
our server and passed audience and scope checks without creating anything.

Then the real one. `propose_claim` through the gateway opened
[PR #66](https://github.com/ostin-pil/aboard/pull/66), claim `ECM2`, with
attribution stamped server-side:

```yaml
authoredBy:
  agent: Smithery Connect
  operator: ostin-pil
  agentId: https://smithery.run/.well-known/oauth-client
```

`operator` came from the verified GitHub login rather than anything the
client sent, which is the provenance upgrade session 31 built, now
demonstrated through a third party.

### 5. A source that did not exist

The claim proposed for the write test needed a real citation. The paper
recalled from memory (Freedman et al. on dietary self-report validation)
is real, but the PMID recalled with it resolves to a veterinary case report
about a dog. Fetching the URL before citing it caught that; a search found
the actual article and its findings were verified against the publisher's
page before anything was written. The rule in `CLAUDE.md` about real source
URLs earned its keep, and the lesson is narrower than "be careful": an
identifier remembered alongside a real paper is exactly the thing that
looks verified and is not.

## Decisions worth remembering

- **A query parameter, not a second path.** RFC 9728 derives the metadata
  document from the path, so one path keeps one metadata document and one
  token audience. A second path would have forked both and needed a second
  resource identifier.
- **Do not read a vendor's generic error as evidence of its internals.**
  `-32001` with an `authorizationUrl` was taken as proof of OAuth
  brokering. The server's own logs said otherwise, and they were available
  the whole time. Reach for `wrangler tail` before inferring what a
  third party did.
- **Public reads plus authenticated writes is an unusual shape.** It is the
  right one for this project, and it falls through the gap in any gateway
  that decides authentication once per connection. Expect to meet this
  again, and `?auth=required` is the answer to hand such a client.
- **Verify every source URL before writing it into the corpus**, including
  identifiers that arrive with a paper that genuinely exists.
- **The static agent token is not the only way in any more.** The first
  outside client authenticated by CIMD, which strengthens session 31's
  open question about whether DCR is still worth keeping.
